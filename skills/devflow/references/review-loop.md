# 「做 / 审」循环

## 审查者怎么选

- 每个审查关卡首轮新派一个 reviewer（批量修复各批除外，见下），用干净上下文（见 SKILL.md「委派 subagent」），不给它作者的思路和自评：作者的解释会让审查者顺着作者的逻辑走。
- 修复核对续用原 reviewer（见「修复的要求」），派出后把它的 ID（Codex 记 task_name）记进 state.md；不再需要续用时关闭它：code review 的 reviewer 在阶段 3 文档审查通过后关闭，阶段 4 回归修复需要再审时按下面的兜底新派；批量修复的 reviewer 在衔接审查结束后关闭。续用不了时（换了会话、被关闭、并发数不够）新派一个干净的，给它上一轮的 must fix 清单和完整产物；同一产物轮次接着算，新产物从第 1 轮算。
- 以下情况新派干净的 reviewer：合入前的最终把关（阶段 4 的验收审查；精简流程由 code review 兼任，不另派）、范围明显变化、作者与 reviewer 僵持不下（连同双方证据交给它裁定）。批量修复每批是新产物，续用同一个 reviewer、从第 1 轮计；全部批次后的衔接审查新派。
- 作者和主 agent 自己审都不算独立审查。环境派不出 reviewer 时告诉用户，按用户意见处理；用户同意自审的（范围按用户说的：整个流程或某个关卡），关卡在 state.md 和汇报里记为"自审完成"，可以推进和推送，但不算审查通过，合入时按 `references/stage4-verify.md` 第 5 节由用户当场决定。
- reviewer 只出具发现，修复归作者。
- 给它：需求/上游文档（它要对照的标准）、验收标准、产物本身（文件路径、diff、PR），以及判断需要的事实：已确认的用户决策和约束、依赖版本与运行环境、验证证据（测试命令和输出）。不给作者的思路、自评和"已经验证过"这类说法。
- 告诉它这一轮重点审什么（见各阶段 reference 的审查要点），以及下面的严重度定义。
- 同一产物默认由一个 reviewer 覆盖全部审查要点；涉及 UI 时可以另派一个 reviewer 只看界面还原度。

## 改动大时拆组

一个 reviewer 面对几十个文件的 diff 审得慢，也容易只看表面。源码改动（不算测试、锁文件、生成文件、快照）超过约 20 个文件或 1000 行、且能分成两组以上时，拆开并行审：

- **分组**：按逻辑单元分（验收标准编号、问题编号或模块），小单元合并，每组大致在这个规模以内。一处逻辑改动（同一函数或相邻的改动块）和它的测试放在同一组。CHANGELOG、问题清单、路由表这类各单元都往里追加的共享文件，以及锁文件、生成文件，归衔接组；其他被几组改到的文件给到每个相关组，各看自己的改动块；分组表写明每个改动块归哪组，归不了组的交衔接组。拆组后不再按维度拆；涉及 UI 时另派一个 reviewer 只看界面还原度。
- **基点**：各组的 diff 都相对同一个基点。常规和整体审查用目标分支的 merge-base（即 PR/MR 的净 diff，不含同步进来的上游改动），在已有分支上做的，在分组表里注明哪些改动是本流程之前就有的；批量修复各批的基点见 SKILL.md「批量修复」。
- **输入**：每组拿到完整的需求和验收标准，写明本组对应哪几条，产物只给本组路径相对基点的最终 diff。另派一个衔接 reviewer，给它需求（方案或问题清单）、验收标准、分组表（每组对应的条目和文件）、全部改动的文件清单和统计，具体代码按需再看；它审归给它的共享文件，并看接口和调用是否对得上、有无重复实现、合起来是否偏离需求、有无验收标准或改动文件没落到任何一组。
- **轮次**：一轮各组都审完、修完再进入下一轮，下一轮续用各组原 reviewer。有 must fix 的组、文件被别组修复改到的组进入下一轮，修复改到组间接口时衔接也进；修复新增的文件归入对应组。每轮由一个参与本轮的 reviewer 跑与改动相关的全部测试。组数超出环境能同时运行的 subagent 数时分批派。

## 严重度

要求 reviewer 给每条发现标下面三级之一，brief 里写明用这套；它自带别的分级时，按影响归入这三级：

- **must fix**：不改就不能进入下一环节——与需求或验收标准不符、正确性/安全问题、会导致返工的设计缺陷、测试造假（为通过而改测试、跳过校验、对特定样例特殊处理）、治标不治本。
- **建议**：改了更好但不影响正确性和后续工作——可读性、命名、小的简化。
- **疑问**：审查者无法确认的假设，需要作者或用户澄清。

## 停止条件

- 循环到没有 must fix 为止。轮次按关卡和产物分别计（同一 reviewer 审新的产物，如阶段 3 的文档改动，也从第 1 轮算）。同一关卡从第 2 轮起，新提出的问题只有正确性/安全缺陷、违反需求或验收标准、测试造假算 must fix，方案审查另加会导致返工的设计缺陷；其他新发现记为"建议"，不再触发新一轮。"建议"由作者酌情采纳，没采纳的按「记录」记，不为建议继续循环。
- "疑问"能由作者用证据回答的就回答；涉及需求取舍的转给用户。
- 没有进展时停下复盘（自测、回归的修复循环同）：上一轮的 must fix 没真正修掉、同一问题反复出现、或修了又冒出同类问题。复盘需求理解有没有错、方案是不是从根上就不对；方向无误就继续循环，需要用户判断的，带着具体分歧找用户。连续 2 轮仍出现同类 must fix，也按没有进展处理。

## 修复的要求

- 作者（主 agent 自己，或续用原 subagent）针对每条 must fix 修复根因，逐条说明怎么改的。
- 作者不同意某条发现时，给出证据反驳。主 agent 不是作者时由它判断谁对；主 agent 就是作者，或拿不准时，带双方证据交 reviewer 复核；仍有分歧时按「审查者怎么选」新派 reviewer 裁定，仍未定再找用户。
- 修复核对时给原 reviewer 上一轮的 must fix 清单、作者逐条的改法和增量 diff，让它确认是否真修了；不附作者对发现的辩解。

## 主 agent 在循环里做什么

- 汇总发现，按「严重度」和「停止条件」校正：风格问题被标成 must fix 的降级，符合 must fix 条件却被标成建议的升级，每次调整连同理由按「记录」记下。主 agent 是作者时，把 must fix 降级要经 reviewer 同意。

## 记录

轮次、结果、未采纳的建议和严重度调整记在 state.md；拆组或批量修复时连同基点和分组表记在工作目录的 `review.md`，state.md 只放指向。
