# 「做 / 审」循环

## 选择审查者

- 每个审查关卡首轮派一名新 reviewer，使用干净上下文；批量修复各批例外见下文。不要提供作者的思路或自评，以免影响独立判断。
- 修复核对续用原 reviewer，按「修复要求」提供材料。派出后将可用于续用的标识记在 `state.md`。无需续用时关闭：阶段 3 代码和文档审查均通过后关闭 code review reviewer；阶段 4 的回归修复若需审查，按下述规则重新派 reviewer；批量修复在衔接审查后关闭 reviewer（见 `references/batch-fix.md`）。
- 若原 reviewer 因会话更换、被关闭或并发数限制而无法续用，就派新 reviewer，使用干净上下文，并提供上一轮 must fix 清单和完整产物。同一产物继续累计轮次，新产物从第 1 轮开始。
- 以下情况须派新的 reviewer 并使用干净上下文：合入前最终把关（阶段 4 验收审查；精简流程由 code review 兼任）、审查范围明显变化、作者与 reviewer 僵持。僵持时附上双方证据，请 reviewer 裁定。批量修复的每批是独立产物，但复用同一 reviewer 并从第 1 轮计；全部批次完成后的衔接审查另派 reviewer（见 `references/batch-fix.md`）。
- 作者或主 agent 自己审查不算独立审查。若环境派不出 reviewer，告知用户并按用户意见处理。用户同意自审时，按其指定范围（全流程或单个关卡）执行；在 `state.md` 和汇报中标记“自审完成”，可继续并推送，但不能记为审查通过。合入时由用户按 `references/stage4-verify.md` 第 5 节当场决定。
- reviewer 只报告发现，修复由作者完成。
- 给 reviewer 提供需求或上游文档、验收标准、待审产物（文件路径、diff、PR），以及判断所需事实：用户决策和约束、依赖版本与运行环境、验证证据（测试命令及输出）。不要提供作者思路、自评或“已经验证过”之类的判断。
- 说明本轮审查重点（见各阶段 reference）和下文严重度标准。
- 默认由一名 reviewer 覆盖同一产物的全部审查要点。涉及 UI 时，可另派 reviewer 只检查界面还原度；负责界面审查的 reviewer 必须拿到实际截图或关键帧图片路径并亲自打开查看，仅靠文字描述不算完成视觉审查。

## 改动大时拆组

源码改动（不含测试、锁文件、生成文件和快照）超过约 20 个文件或 1000 行，且能分成两组以上时，拆组并行审查。这样可让 reviewer 聚焦逻辑单元。

- **分组**：按验收编号、问题编号或模块等逻辑单元划分，小单元可合并，每组尽量控制在上述规模内。同一逻辑改动及其测试放在一组。CHANGELOG、问题清单、路由表等共享文件，以及锁文件和生成文件归入衔接组；其他被多组改动的文件分配给相关组，各组只审自己的改动块。分组表须标明改动块所属组；无法归组的改动交衔接组。拆组后不再按审查维度拆分；涉及 UI 时，必须另派一名 reviewer 专门检查界面还原度，并向其提供实际截图或关键帧图片路径供打开核对。
- **基点**：所有组使用同一基点。常规或整体审查以目标分支的 merge-base 为基点，即 PR/MR 净 diff，不含同步进来的上游改动。已有分支上开始的工作，须在分组表标明哪些改动早于本流程。批量修复各批基点见 `references/batch-fix.md`。
- **输入**：每组获得完整需求和验收标准，并注明本组对应条目；只提供本组文件相对基点的最终 diff（各组 brief 共用部分在前、本组差异在后）。另派衔接 reviewer，提供需求（方案或问题清单）、验收标准、分组表（各组条目和文件）、全部改动的文件清单与统计；代码按需提供。衔接 reviewer 审共享文件，并检查接口和调用是否匹配、有无重复实现、合并结果是否偏离需求，以及验收标准或改动文件是否漏组。
- **轮次**：一轮所有组都审完、修完后才进入下一轮。下一轮续用原 reviewer。有 must fix 的组，以及被其他组修复改动触及的组，进入下一轮；修复影响组间接口时，衔接组也复审。新增文件归入对应组。每轮由一名参与本轮的 reviewer 运行与改动相关的全部测试。若组数超过环境可同时运行的 subagent 数量，分批派发。

## 严重度

要求 reviewer 将每条发现标为以下三级之一，并在 brief 中说明。若 reviewer 使用其他分级，按影响映射到这三级：

- **must fix**：不修就不能进入下一环节，包括违反需求或验收标准、正确性或安全问题、会导致返工的设计缺陷、测试造假（为通过而改测试、跳过校验、针对特定样例特殊处理）以及治标不治本。
- **建议**：改了更好，但不影响正确性或后续工作，如可读性、命名和小幅简化。
- **疑问**：审查者无法确认的假设，需要作者或用户澄清。

## 停止条件

- 循环至没有 must fix 为止。轮次按关卡和产物分别计数。同一关卡从第 2 轮起，新发现只有正确性或安全缺陷、违反需求或验收标准、测试造假才标 must fix；方案审查还包括会导致返工的设计缺陷。其他新发现记为“建议”，不触发新一轮，由作者酌情采纳；未采纳项按「记录」处理。
- 作者能用证据回答的“疑问”由作者回答；涉及需求取舍的交用户决定。
- 若无进展，暂停循环并复盘：上一轮 must fix 没有修好、同一问题反复出现，或修复后又出现同类问题。检查需求理解和方案根因；方向正确则继续。需要用户判断时，带具体分歧请用户决定。连续两轮出现同类 must fix 也按无进展处理。自测和回归修复循环同样适用。

## 修复要求

- 作者（主 agent 或续用的原 subagent）针对每条 must fix 修复根因，并逐条说明改法。
- 作者不同意发现时，提供证据反驳。若主 agent 不是作者，由主 agent 判断；若主 agent 是作者或无法判断，将双方证据交 reviewer 复核。仍有分歧时按「选择审查者」另派 reviewer 裁定；仍未解决再问用户。
- 修复核对时，给原 reviewer 上一轮 must fix 清单、作者逐项改法和增量 diff；不要附作者对发现的辩解。

## 主 agent 在循环中的职责

- 汇总发现并校准严重度：风格问题标成 must fix 时降级；符合 must fix 定义却标成建议时升级。调整时连理由一起记入记录。若主 agent 同时是作者，must fix 降级须经 reviewer 同意。

## 记录

常规审查在 `state.md` 记录轮次、结果、未采纳建议和严重度调整。拆组或批量修复时，在工作目录的 `review.md` 记录这些内容以及基点和分组表；`state.md` 只保留 `review.md` 的指向。
