# 「做 / 审」循环

## 审查者怎么选

- 每轮新派一个 reviewer，不给它上一轮的讨论、作者的思路和自评：作者的解释会让审查者顺着作者的逻辑走。
- reviewer 只出具发现，修复归作者。
- 只给它三样东西：需求/上游文档（它要对照的标准）、验收标准、产物本身（文件路径、diff、PR）。
- 告诉它这一轮重点审什么（见各阶段 reference 的审查要点），以及下面的严重度定义。
- 同一产物涉及多个维度（如代码既有逻辑又有 UI）时，可以并行派多个 reviewer，各审一个维度。

## 严重度

要求 reviewer 给每条发现标下面三级之一，brief 里写明用这套；它自带别的分级时，按影响归入这三级：

- **must fix**：不改就不能进入下一环节——与需求或验收标准不符、正确性/安全问题、会导致返工的设计缺陷、测试造假（为通过而改测试、跳过校验、对特定样例特殊处理）、治标不治本。
- **建议**：改了更好但不影响正确性和后续工作——可读性、命名、小的简化。
- **疑问**：审查者无法确认的假设，需要作者或用户澄清。

## 停止条件

- 不设轮数上限，循环到没有 must fix 为止。"建议"由作者酌情采纳，没采纳的记进 state.md，不为建议继续循环。
- "疑问"能由作者用证据回答的就回答；涉及需求取舍的转给用户。
- 没有进展时停下复盘：上一轮的 must fix 没真正修掉、同一问题反复出现、或修了又冒出同类问题。复盘需求理解有没有错、方案是不是从根上就不对；方向无误就继续循环，需要用户判断的，带着具体分歧找用户。新一轮 reviewer 提出新的、不同的问题，属于正常进展。

## 修复的要求

- 作者（续用原 subagent）针对每条 must fix 修复根因，逐条说明怎么改的。
- 作者不同意某条发现时，给出证据反驳；主 agent 判断谁对，拿不准就交给下一轮 reviewer 裁定。
- 下一轮 reviewer 收到的仍只有：需求、验收标准、修改后的产物；可以附上上一轮的 must fix 清单让它确认是否真修了，不附作者的解释。

## 主 agent 在循环里做什么

- 汇总发现，校正严重度：风格问题被标成 must fix 的降级，真问题被标成建议的升级。
- 把轮次和结果记到 state.md。
