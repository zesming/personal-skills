# 阶段 1：产品方案

产品方案只写做什么、为谁、做到什么程度，不写怎么实现。

## 1. 收集上下文（并行）

派 explorer 并行查三类信息，主 agent 只看结论：

- **用户输入**：请求原文、给出的附件、链接、截图。
- **本地现状**：相关功能现在怎么工作、涉及哪些模块和页面、已有的产品/设计/技术文档、已有的测试。
- **外部调研**：同类产品或社区里这个问题通常怎么解决、有哪些常见坑、用户预期是什么。默认要做，只查会影响方案的问题；派出前根据请求和初步了解判断，已收集的信息确实足以支撑决策时才跳过。

## 2. 与用户澄清

找出真正需要用户决定的点：需求有多种理解且结果差异大、存在实质取舍、范围不清、缺少只有用户知道的信息。按 SKILL.md「与用户沟通」提问，另外：

- 每个问题附 2–4 个具体选项，推荐项放第一个并说明理由。
- 问题要具体：问"`cancel_order` 目前不回补库存，这次要一起补上吗？"，而不是"需要处理库存吗？"。
- 能合理默认的不问，写进方案的「假设」一节。
- 只有第一轮的回答引出了新的关键不明确点时才追问，追问同样精简。

## 3. 写产品方案

designer 按 `assets/templates/product.md` 产出方案正文，并按 `assets/templates/acceptance.md` 产出用户验收用例；主 agent 分别写入 `.devflow/<需求>/product.md` 和 `.devflow/<需求>/acceptance.md` 的「用户验收」部分。

用户验收用例每条编号 `AC-xx`，从用户视角写 Given/When/Then，覆盖主流程、关键边界和异常；写成可执行、可观察的，不写"体验良好"这类说法。

## 4. 交互原型（涉及 UI 时）

worker 按产品方案制作 `.devflow/<需求>/prototype.html`：

- 单个自包含的 HTML 文件，本地浏览器直接打开，不依赖构建和外部服务。
- **低保真、可交互**：灰阶线框即可，但要能点击走通主要用户旅程，覆盖关键状态（空、加载、错误、成功）；视觉细节留给阶段 2 的设计稿。
- 非 Web 平台（移动端、鸿蒙等）也用 HTML 模拟页面流转。
- 在原型里标注对应的 `AC-xx`。

## 5. 审查

按 `references/review-loop.md` 执行。给 reviewer：用户原始请求、澄清记录（用户决策）、product.md、acceptance.md、prototype.html。审查要点：

- 方案是否回应了用户的真实问题，有没有更简单的方案能达到同样目标。
- 范围是否清晰，有无遗漏的场景或隐含的范围蔓延。
- 是否混入了实现细节。
- 验收用例是否覆盖主流程、边界和异常，每条是否可观察、可执行。
- 原型能否走通旅程，与方案描述是否一致。

## 完成标准

无 must fix；state.md 记录关卡通过和用户决策；向用户简要汇报后进入阶段 2。
