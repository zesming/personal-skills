# 阶段 1：产品方案

产品方案说明做什么、为谁做、成功标准是什么以及如何验收，不写实现方式。

## 1. 收集上下文

收集以下信息。产品方案需要的本地现状由主 agent 查看；会产生大量临时输出的外部调研交给 explorer，只取结论。

- **用户输入**：原始请求、附件、链接和截图。
- **本地现状**：相关功能的当前行为、涉及的模块和页面、现有产品/设计/技术文档及测试。
- **外部调研**：同类产品或社区如何解决类似问题、常见问题和用户预期。默认调研会影响方案的关键问题；初步了解后若已有信息足以支持决策，可以跳过。

## 2. 与用户澄清

只询问必须由用户决定的内容：不同理解会导致明显不同结果、有实质取舍、范围不清，或缺少只有用户掌握的信息。按 SKILL.md「与用户沟通」提问；可合理默认的内容写入方案的「假设」一节。

- 每题给 2–4 个具体选项，把推荐项放在第一位并说明理由。
- 问清具体决策。例如：“`cancel_order` 目前不回补库存，这次要一起补上吗？”，不要只问“需要处理库存吗？”。
- 只有首轮回答引出新的关键疑问时才追问；追问也要简短、聚焦。

## 3. 写产品方案

主 agent 按 `assets/templates/product.md` 编写 `.devflow/<需求>/product.md`，按 `assets/templates/acceptance.md` 编写用户验收部分，存为 `.devflow/<需求>/acceptance.md`。

- 用户验收用例编号为 `AC-xx`，覆盖本次每个设计点和用户路径中的主流程、关键边界与异常。用户可感知的非功能要求（如等待时长、平台支持、权限）也要验收。
- 使用用户视角的 Given/When/Then。每项都要可执行、可观察；不写“体验良好”之类的主观标准，也不描述点击哪个按钮等界面操作。
- 列出验收前提和必须由用户亲自验证的项目（如真机、真实外部服务或主观判断）。若需要用户提供账号、设备、沙箱凭据或数据，本阶段就问清。凭据只存于环境变量或 `.devflow/`，不得入库。

## 4. 交互原型（涉及 UI 时）

依据产品方案制作 `.devflow/<需求>/prototype.html`，可交给 worker 完成。

- 使用一个自包含的 HTML 文件，可在本地浏览器直接打开，不依赖构建流程或外部服务。
- 原型应低保真且可交互：用灰阶线框即可，但须能点击走通主要用户旅程，并覆盖关键状态（空、加载、错误、成功）；视觉细节留给阶段 2 的设计稿。
- 移动端、鸿蒙等非 Web 平台也用 HTML 模拟页面流转。
- 标注每个页面或状态对应的 `AC-xx`。

## 5. 审查

按 `references/review-loop.md` 执行。提供给 reviewer：用户原始请求、澄清和决策记录、`product.md`、`acceptance.md`，以及涉及 UI 时的 `prototype.html`。

重点检查：

- 方案是否解决用户的真实问题，是否存在更简单且同样有效的做法。
- 范围是否清楚，是否遗漏场景或无意扩大范围。
- 是否混入实现细节。
- 验收是否覆盖各设计点和用户路径；每项是否可观察、可执行；验收前提和用户亲验项是否齐全。
- 原型能否走通主要旅程，是否与方案一致。

## 完成标准

没有 must fix；`state.md` 已记录关卡结果和用户决策。向用户简要汇报后进入阶段 2。
