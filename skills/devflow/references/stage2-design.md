# 阶段 2：实现方案

基于产品方案产出技术方案和设计方案（涉及 UI 时）。两者可以并行，最后确认彼此一致。

输入：`.devflow/<需求>/product.md`、`prototype.html`、`acceptance.md`。

T-xx / D-xx 由 designer 在返回中给出，主 agent 合并写入 `.devflow/<需求>/acceptance.md`。

## 1. 技术方案

designer 按 `assets/templates/tech.md` 产出正文，主 agent 写入 `.devflow/<需求>/tech.md`。

- **先看现有实现**：相关模块的结构、已有的模式和约定、可复用的部分。沿用项目已有做法优先于引入新东西。
- **有已知方向时调研最佳实践**：如要做的东西社区有成熟方案（缓存策略、鉴权、状态管理、某类组件），派 explorer 查社区/GitHub 的主流做法和已知坑；已收集的信息足够支撑决策时可以跳过。
- 从满足验收标准的最简方案入手，规模与需求相称。
- **测试策略**：项目没有 e2e 设施时，在这里按项目技术栈最常规的做法提出搭建方案，作为需要用户拍板的点，不拖到阶段 4。
- **技术验收标准**：编号 `T-xx`，写明对应哪些 `AC-xx`、可验证的技术条件（接口行为、数据一致性、性能指标、错误处理）和验证方式（单测、集成测试、命令）。

## 2. 设计方案（涉及 UI 时）

designer 产出设计说明正文，主 agent 写入 `.devflow/<需求>/design.md`；worker 按设计说明制作 `.devflow/<需求>/design.html`。

- design.html 是高保真、可交互的 HTML 设计稿：使用项目现有的设计规范（颜色、字体、间距、组件库、图标），看起来就是产品的一部分。先找项目里的 design tokens、主题文件、组件库，没有的话从现有页面提取。
- 覆盖与本需求相关的状态（如加载、空、错误、禁用）和关键交互反馈，不相关的状态不画；覆盖需要适配的尺寸或平台。
- 界面方向有实质不确定时，可以派 explorer 调研同类产品的做法。
- design.md 说明设计决策、组件复用关系、与原型的差异及原因。
- **设计验收标准**：编号 `D-xx`，对应 `AC-xx`，写明可检查的视觉与交互条件（布局、状态表现、交互反馈）。

## 3. 与用户讨论

两份方案中需要用户拍板的点（实质取舍、引入新依赖、改公共接口、设计方向选择），按阶段 1 第 2 节的方式集中讨论。

## 4. 审查

按 `references/review-loop.md` 执行：两份方案各自审查，再做一次交叉一致性检查。

技术方案的审查要点：
- 是否满足产品方案和全部 AC，有无更简单的做法。
- 与现有架构是否一致，是否引入不必要的复杂度或依赖。
- 失败模式、兼容性、安全性是否考虑到。
- T-xx 是否可验证，是否覆盖了所有 AC。

设计方案的审查要点：
- 是否忠于产品方案和原型的流程，偏离处是否有理由。
- 是否符合项目设计规范，状态是否齐全。
- D-xx 是否可检查。

交叉检查（一个 reviewer 同时拿到两份方案）：
- 技术方案能否支撑设计稿里的每个交互和状态（如设计稿有加载进度，接口是否提供）。
- AC → T/D 的映射有无遗漏。

## 完成标准

两份方案和交叉检查都无 must fix，state.md 已更新；向用户简要汇报后进入阶段 3。
