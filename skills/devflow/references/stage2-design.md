# 阶段 2：实现方案

基于产品方案编写技术方案；涉及 UI 时同时编写设计方案。两份方案由主 agent 编写，完成后核对一致性。`design.html` 可交给 worker 与技术方案并行制作。

输入：`.devflow/<需求>/product.md`、`acceptance.md`，以及涉及 UI 时的 `prototype.html`。

主 agent 将 D-xx、T-xx 和 AC 的落地方式写入 `.devflow/<需求>/acceptance.md`。

## 1. 技术方案

主 agent 按 `assets/templates/tech.md` 编写 `.devflow/<需求>/tech.md`。

- **先了解现状**：检查相关模块的结构、已有模式和约定，以及可复用部分。优先沿用项目做法，不轻易引入新方案。
- **调研成熟做法**：对缓存、鉴权、状态管理或组件等已有成熟方案的方向，若现有信息不足以支持决策，派 explorer 调研社区/GitHub 的主流做法和已知问题。现有信息足够时可以跳过。
- 从满足验收标准的最简方案开始，确保方案规模与需求相称。
- **落实验收**：为每条 AC 和 D 选择落地方式；阶段 1 标为用户亲验的项目仍保留，可同时增加自动化验证。选择能观察到结果的最低测试层，主要用户路径使用 e2e。无法自动化的标为人工并说明原因。截图基线应在与 CI 相同的环境生成。若项目缺少所需测试设施，按技术栈常规做法提出搭建方案，并列为需用户决定的事项。实现本身的单元测试按工程惯例添加，不在此处逐项设计。
- **补充技术验收**：若技术方案引出 AC、D 未覆盖的性能、安全、兼容、迁移或回滚要求，将其编号为 `T-xx`，写明可度量的通过标准和验证方式。没有额外要求时不写 T。

## 2. 设计方案（涉及 UI 时）

主 agent 编写设计说明 `.devflow/<需求>/design.md`；worker 根据说明制作 `.devflow/<需求>/design.html`。

- `design.html` 是高保真、可交互的 HTML 设计稿。沿用项目的设计规范、tokens、主题、组件和图标，无规范时以现有页面为基线。
- 有视觉参考时，在 `design.md` 写明采用哪些特征。新增页面或调整视觉方向时，写清适用的图像类型与用途、字体层级和目标尺寸，可引用现有规范。
- 覆盖受影响的尺寸、平台、状态和关键交互反馈。同页同状态下，针对同一对象且结果相同的操作只留一个可见入口，确保键盘和读屏仍可用。文案只保留理解、判断、操作、状态反馈或明确内容要求所需的信息，包括必要的风险和恢复指引。
- 设计方向有实质不确定时，可派 explorer 调研同类产品。
- `design.md` 记录设计决策、复用的组件，以及相对原型的改动和原因。
- **定义设计验收**：每项设计验收编号为 `D-xx`，针对本次样式和交互变化，列出可检查条件（如布局、状态、反馈和适配尺寸），并指出 `design.html` 中对应的页面与状态。AC 已覆盖的行为不重复列入 D。D 确定后，将其落地方式填入 `acceptance.md`，并与技术方案一起审查。

## 3. 与用户讨论

集中讨论需要用户决定的事项，如实质取舍、新依赖、公共接口变更或设计方向。提问方式见阶段 1 第 2 节。

## 4. 审查

按 `references/review-loop.md` 执行。默认由一名 reviewer 同时审查两份方案和 `acceptance.md`，并检查它们是否一致。方案较大时可分别交技术和设计 reviewer，其中一人负责交叉检查。

技术方案重点检查：

- 是否满足产品方案及全部 AC，是否有更简单的做法。
- 是否符合现有架构，有无不必要的复杂度或依赖。
- 是否考虑失败模式、兼容性和安全性。
- 每条 AC、D、T 是否有落地方式，测试层级是否合适，人工验证理由是否充分，非功能要求是否遗漏。

设计方案重点检查：

- 是否遵循产品方案和原型流程；偏离处是否说明原因。
- 渲染受影响的尺寸和状态，对照设计规范及适用的视觉参考，检查文案、操作入口和反馈。
- D-xx 是否覆盖本次样式和交互变化，且可检查。

交叉检查（同一 reviewer 同时审两份方案时）：

- 技术方案是否支持设计稿中的所有交互和状态（例如设计稿展示加载进度时，接口是否提供所需信息）。
- 设计稿中的状态和交互是否均由 D 或 AC 覆盖；每条 D 在技术方案中是否有可行的落地方式。

## 完成标准

技术方案，以及涉及 UI 时的设计方案和交叉检查，均无 must fix；`state.md` 已更新。向用户简要汇报后进入阶段 3。
