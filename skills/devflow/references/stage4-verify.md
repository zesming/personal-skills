# 阶段 4：回归与合入

## 1. 治理测试集

派 explorer 盘点与本次改动相关的已有测试（e2e、集成、截图基线）：用什么框架、怎么运行、覆盖哪些功能。对照 acceptance.md 的落地方式（批量修复为 review.md 里各条目的验证记录）和项目文档中描述的功能（阶段 3 已更新到最新）：

- **过时/失效**：测试的功能已被移除或行为已按方案改变、选择器失效、断言已不反映预期行为的，删除或更新；每删一条都写明理由。
- **缺失**：本次应落地却没有的用例，按落地方式补上。

本阶段增删改的用例，编号对应记在 regression.md。

## 2. 全量回归

运行全部测试（e2e、集成、单测、截图基线，不只是新用例）和构建。失败时先定位根因：

- 新改动引入的回归：回到阶段 3 修复。修复也要经过 review；行为有变化时同步更新已整合的项目文档，一起审。
- 测试本身过时：按第 1 节处理。
- 不稳定（flaky）：找出原因修掉，不用"重跑直到通过"掩盖。已有的 flaky 用例原因不在本次改动范围内的，报告给用户，不深挖。
- 主干上本来就失败的（在主干上复跑确认）：不擅自扩大范围去修，报告给用户决定。

结果写到 `.devflow/<需求>/regression.md`：跑了什么、结果、修复了什么；人工项和用户亲验的模拟在取证后又受改动影响的（含 code review 的修复），重走并记在这里。

## 3. 验收审查

回归通过后，对整体走一次「做 / 审」。给 reviewer：product.md、design.md/design.html、acceptance.md、selftest.md、regression.md、PR 和本阶段的测试改动 diff（批量修复以问题清单、review.md 中各批的验证记录代替前四项）。重点看：
- 每条 AC、D、T 是否都有按落地方式、在最后一次相关改动之后取得的通过证据（用户亲验的看模拟结果或注明），人工项是否真的走过；
- 本阶段新增或修改的用例是否真的验证了对应编号的可观察结果；
- 测试的删除和修改是否有正当理由，有无为了通过而删测试、放宽断言、加 skip。

## 4. 更新 PR/MR

所有测试通过后，把测试改动和回归期间的修复推到同一个 PR/MR，更新 PR 描述中的验证部分（在已有 PR/MR 上做的，按 stage3 第 1 节用评论补充）。

## 5. 合入（必须经用户确认）

检查合入条件，全部满足才向用户申请合入（自审、用户亲验两条除外，见下）：

- [ ] CI 全部通过（仓库没有 CI 时注明，以本地全量回归为准）
- [ ] 在最终提交上，本地全量回归通过（主干上本来就失败、经用户确认可以忽略的除外）
- [ ] 最后一轮 code review 和验收审查无 must fix，且之后没有未审的改动（自审的如实标明：此条视为不满足，事先授权不适用，由用户看过后当场决定是否合入）
- [ ] 与目标分支无冲突，分支是最新的
- [ ] 文档已随 PR 更新
- [ ] 目标分支的保护规则允许合入（所需的 approval 等）
- [ ] 用户亲验的条目已由用户确认

向用户展示：PR 链接、条件清单、变更摘要、需要用户亲验的条目和验证方法、遗留风险，并问要保留哪些过程产物（见 stage5 第 1 节）。**用户明确确认后**才执行合入（用户事先已明确授权合入的，条件全部满足后可直接合入，汇报时附上条件清单；授权不覆盖条件不满足和用户亲验），合并方式遵循仓库惯例（squash/merge/rebase）。任一条件不满足时，报告卡在哪里以及建议的处理方式，不强行合入。用户亲验不通过的，按回归失败回到阶段 3。

用户不同意合入时问清是放弃还是暂缓，按阶段 5 开头处理。合入或用户放弃后进入阶段 5。
