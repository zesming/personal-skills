# 阶段 4：回归与合入

## 1. 盘点测试集

派 explorer 盘点项目现有的 e2e/集成测试：用什么框架、怎么运行、覆盖了哪些功能模块。然后对照：

- 本次的 `AC-xx`（以及 `D-xx` 中需要视觉/交互验证的部分）；
- 项目已有的产品/设计文档中描述的功能（阶段 3 已更新到最新）。

得出三份清单：
- **缺失**：本次新增或改动的功能没有 e2e 覆盖的，补上；与本次无关的已有功能缺覆盖的，列进遗留风险报告用户，不在本 PR 补。用例名称描述用户行为（如"取消已支付订单后收到退款"），不写 AC 编号（工作目录删除后编号会悬空）；AC 与用例的对应关系记在 regression.md。
- **过时/失效**：测试的功能已被移除或行为已按方案改变、选择器失效、断言已不反映预期行为的，删除或更新；每删一条都写明理由。
- **保持**：其余正常的用例。

e2e 设施按阶段 2 技术方案里确定的测试策略使用或搭建；方案里没有覆盖到、需要新引入依赖时，先问用户。

## 2. 测试改动的审查

测试集的改动走一次「做 / 审」，reviewer 重点看：
- 新用例是否真的验证了 AC 描述的用户可观察行为；
- 每条删除/修改是否有正当理由，是否有为了让测试通过而删测试、放宽断言、加 skip 的情况。

## 3. 全量回归

运行完整的 e2e 回归（不只是新用例）以及单测、构建。失败时先定位根因：

- 新改动引入的回归：回到阶段 3 修复。修复也要经过 review；行为有变化时同步更新已整合的项目文档，一起审。
- 测试本身过时：按第 1 节处理。
- 不稳定（flaky）：找出原因修掉，不用"重跑直到通过"掩盖。已有的 flaky 用例原因不在本次改动范围内的，报告给用户，不深挖。
- 主干上本来就失败的（在主干上复跑确认）：不擅自扩大范围去修，报告给用户决定。

修复 ↔ 回归连续几轮没有进展时，按 `references/review-loop.md` 停下复盘。结果写到 `.devflow/<需求>/regression.md`：跑了什么、结果、修复了什么。

## 4. 更新 PR/MR

所有测试通过后，把测试改动和回归期间的修复推到同一个 PR/MR，更新 PR 描述中的验证部分（在已有 PR/MR 上做的，按 stage3 第 1 节用评论补充）。

## 5. 合入（必须经用户确认）

检查合入条件，全部满足才向用户申请合入（自审一条除外，见下）：

- [ ] CI 全部通过（仓库没有 CI 时注明，以本地全量回归为准）
- [ ] 本地全量回归通过（主干上本来就失败、经用户确认可以忽略的除外）
- [ ] 最后一轮 code review 和测试审查无 must fix 问题（自审的如实标明：此条视为不满足，事先授权不适用，由用户看过后当场决定是否合入）
- [ ] 与目标分支无冲突，分支是最新的（为此 rebase/merge 过主干的，合并后重跑全量回归）
- [ ] 文档已随 PR 更新
- [ ] 目标分支的保护规则允许合入（所需的 approval 等）

向用户展示：PR 链接、条件清单、变更摘要、遗留风险，并问要保留哪些过程产物（见 stage5 第 1 节）。**用户明确确认后**才执行合入（用户事先已明确授权合入的，条件全部满足后可直接合入，汇报时附上条件清单；授权不覆盖条件不满足的情况），合并方式遵循仓库惯例（squash/merge/rebase）。任一条件不满足时，报告卡在哪里以及建议的处理方式，不强行合入。

合入或用户决定不合入后进入阶段 5。
