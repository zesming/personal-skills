# 阶段 4：回归与合入

## 1. 治理测试集

盘点本次改动涉及的现有测试，包括 e2e、集成测试和截图基线：记录使用的框架、运行方式和覆盖功能。测试多或分布广时，可派 explorer 并行调查。

对照 `acceptance.md` 的落地方式（批量修复则对照 `review.md` 中各条目的验证记录）和阶段 3 已更新的项目文档：

- **过时或失效的用例**：功能已移除或行为已按方案改变、选择器失效、断言不再代表预期行为时，删除或更新用例。每项删除都说明理由。
- **缺失的用例**：本次按验收要求应有但尚不存在的用例，按对应落地方式补齐。

本阶段新增、删除或修改的用例，其对应编号记在 `regression.md`。

## 2. 全量回归

运行全部测试（e2e、集成、单元和截图基线），并运行构建。失败时先定位根因，再按类型处理：

- **新改动引入回归**：返回阶段 3 修复，并经过 review。行为变化时同步更新已整合的项目文档，一起审查。
- **测试已过时**：按第 1 节治理。
- **不稳定（flaky）**：找出并修复原因，不要反复重跑来掩盖问题。若已有 flaky 与本次改动无关，报告给用户，不深入排查。
- **主干原有失败**：在主干复跑确认后报告用户决定，不擅自扩大范围修复。

结果记入 `.devflow/<需求>/regression.md`，包含运行项目、结果和修复内容。人工项以及用户亲验项的模拟结果若在取证后受改动影响（包括 code review 修复），重新验证并记录。

## 3. 验收审查

回归通过后，对整体再走一次「做 / 审」。提供给 reviewer：`product.md`、`design.md`/`design.html`、`acceptance.md`、`selftest.md`、`regression.md`、PR（尚未创建时提供本地净 diff），以及本阶段测试改动的 diff。批量修复时，用问题清单和 `review.md` 中各批验证记录代替前四项。

重点检查：

- 每条 AC、D、T 是否按其落地方式，在最后一次相关改动后取得通过证据。用户亲验项要提供模拟结果或注明仍需用户确认；人工项须实际走查。
- 本阶段新增或修改的用例是否验证对应编号所描述的可观察结果。
- 测试删除或修改是否有正当理由；是否为了通过而删测试、放宽断言或加 skip。

## 4. 更新 PR/MR

回归和验收审查通过后，已有 PR/MR 按授权推送最终改动并按 stage3 第 1 节更新验证记录。明确约定此时首次发布时，沿用交接记录的授权、公开检查和报告发布约定。满足条件后，向已登记的目标分支开 PR/MR，写入验证结果并登记链接；未满足时留本地。

## 5. 合入（必须经用户确认）

除待用户亲验和自审例外外，以下条件满足后发起合入确认。可在同一次询问中请用户完成亲验并决定是否合入。

- [ ] CI 全部通过；仓库没有 CI 时注明，并以本地全量回归为准。
- [ ] 最终提交上的本地全量回归通过；主干原有失败只有在用户确认可忽略时例外。
- [ ] 最后一轮 code review 和验收审查均无 must fix，之后没有未审改动。若为自审，如实标明此项不满足；事先授权不适用，由用户审阅后当场决定是否合入。
- [ ] 分支是最新的，且与目标分支无冲突。
- [ ] 文档已随 PR 更新。
- [ ] 目标分支保护规则允许合入，包括所需 approval。
- [ ] 用户亲验项已由用户确认。

向用户展示 PR 链接、条件清单、变更摘要、需用户亲验的项目及验证方法、遗留风险，并询问要保留哪些过程产物（见 stage5 第 1 节）。**适用条件满足、所需亲验通过且取得合入确认后**执行合入。用户已事先明确授权，且全部条件满足时可直接合入，汇报时附条件清单。按仓库惯例选择 squash、merge 或 rebase。

任一条件未满足时，说明阻塞项和建议的处理方式，不强行合入。用户亲验未通过时，按回归失败返回阶段 3。

用户不同意合入时，问清是放弃还是暂缓，并按阶段 5 开头处理。合入或用户放弃后进入阶段 5。
