# 阶段 3：开发

## 1. 准备

- 从最新主干创建功能分支，并登记到 `state.md`。工作区有用户未提交的改动时，先询问用户如何处理；不要自行 stash 或覆盖。
- 用户或清单指定分支时沿用该分支。已有 PR/MR 时沿用，并按约定更新描述和验证评论。仅指定分支时，只有用户或清单明确要求开 PR/MR，才在约定时点创建。已有分支和 PR/MR 不登记为本流程创建的资源。推送前须通过 code review。
- 按技术方案拆分实现任务。默认由主 agent 连续实现；仅在任务互不依赖、改动文件不重叠且规模值得并行时交给 worker。有关联的任务按顺序执行。

## 2. 实现

- 沿用项目约定，针对根因修复。从实际入口核对受影响的调用方和已有数据。复用语义兼容的逻辑，保留需求范围外的既有行为。用清楚的命名和直观的控制流，抽象应简化职责或消除实际重复。
- 按用户要求、项目约定和验收方式补足测试，优先扩展现有用例。其余仅补能检出现有测试遗漏的具体回归。测试按用户行为命名，验收编号另记。按方案搭建测试设施，未定的新依赖先征求用户同意。凭据不入库。

委派 worker 时，brief 还要给出相关方案章节（`tech.md`、`design.md`/`design.html` 的路径）、文件范围、需满足的验收编号与落地方式，以及上述实现约束。

## 3. 自测

合并各任务后，按 `acceptance.md` 逐条验证。主 agent 负责验证，也可交给 worker。结果记入 `.devflow/<需求>/selftest.md`；每项写明通过或未通过、证据和对应测试用例。

- 自动化项运行对应测试；人工项实际运行应用并走查。界面项按 SKILL.md「验证手段」对受影响的尺寸和状态截图（动画或多步交互流程截关键帧序列；宿主支持视频输入时可用短录屏），**逐张打开图像检查**并与 `design.html`（精简档位则与现有页面基线）对照，在 `selftest.md` 记录截图路径与核对结果。用户亲验项能在本地或测试环境模拟的先模拟；无法模拟时在 `selftest.md` 说明。
- 另外运行项目常规检查：单元测试、构建、lint 和类型检查。

有未通过项时返回实现阶段修复，不带着已知问题进入 review。

## 4. Code review

按 `references/review-loop.md` 执行。提供给 reviewer：产品方案、技术方案、设计方案、验收标准、完整 diff 和 `selftest.md`；涉及 UI 时一并提供实现截图或关键帧图片路径（由负责界面检查的 reviewer 亲自打开对照，文字描述不算视觉审查）。默认由一名 reviewer 覆盖全部要点；涉及 UI 时可另派一名 reviewer 只检查界面还原度；大改动按 `references/review-loop.md`「改动大时拆组」。

重点检查：

- 正确性、安全性、边界与异常处理，核对实际入口及与既有调用方、数据的兼容性。
- 实现是否符合方案；偏离是否合理并同步更新方案。
- 实现是否直接、简单，有无补丁式绕路、过度抽象或重复代码。
- 是否符合项目风格和架构，是否便于维护。
- 验收测试是否按落地方式编写，是否验证对应编号描述的可观察结果，是否按用户行为命名。测试造假的定义见 review-loop「严重度」。
- 自测结果是否可信。负责跑测试的 reviewer 应复跑；若其无法运行，由主 agent 按 reviewer 指定命令执行，并把完整输出交给 reviewer。

## 5. 文档整合（与代码同一个 PR）

将过程方案中长期有用的信息整合进项目文档（可与代码一并提交第 4 节 code review，也可在代码 review 通过后作为增量补交）：

- 先查明项目的产品、技术/架构和设计文档位置（如 `docs/`、`doc/`、wiki 或模块 README），再把相关内容合入对应文档，不要原样复制过程文档。项目没有合适文档，且内容确有长期保留价值时，建立最小文档结构。
- 按读者的任务组织内容，先给结论或操作入口。沿用项目术语，补齐独立理解或执行所需的前提。
- 更新时核对受影响内容与系统现状，保留无关原文。同一读者、同一任务的重复说明集中到主文档，其他入口保留就地所需的前提、风险、恢复指引和链接。
- README 仅保留当前项目的简要介绍和使用说明，不写开发过程、迭代历史或“本次新增了什么”。
- 按项目现有格式在 CHANGELOG 中增加面向使用者的变化说明。
- 若文档已随第 4 节代码一并送审且内容与最终代码一致，可同轮完成审查；否则作为同一 PR 的增量交原 code reviewer 审查。重点检查与代码现状一致、内容精简且无过程描述或过时信息。

## 6. 提交 PR/MR

- 按项目现有提交规范编写 commit message。
- 结合仓库 remote 和本机可用工具确定提交方式；无法判断时询问用户。
- PR 描述写清改动内容、原因、验证方式和结果（按用户行为列项）、风险及回滚方法，不写过程讨论。已有 PR/MR 按第 1 节处理，不重写描述。
- 将 PR 链接登记到 `state.md`。约定验证后再开 PR/MR 时，先记录源分支、目标分支和交付时点，用本地净 diff 进入阶段 4，第 4 节统一推送和开 PR/MR。
