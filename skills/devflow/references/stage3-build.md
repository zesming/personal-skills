# 阶段 3：开发

## 1. 准备

- 从最新的主干切功能分支，登记到 state.md。工作区有用户未提交的改动时先问用户怎么处理，不擅自 stash 或覆盖。
- 用户或问题清单的修复约定指定了已有的分支或 PR/MR（接手已开的 MR、按审查报告修复等）时，就在它上面做：不另切分支、不另开 PR/MR，不登记为本流程创建的资源（收尾不删）；往它推送同样要等 code review 无 must fix；它的描述只按已有约定更新（如勾选清单），验证情况用评论补充。
- 按技术方案把实现拆成任务：互不依赖、改动文件不重叠的可以分给多个 worker 并行，有依赖的按顺序执行。

## 2. 实现

给 worker 的 brief 包含：对应的方案章节（tech.md、design.md/design.html 的路径）、要改的文件范围、要满足的验收编号及其落地方式、约束（沿用项目约定、不改无关代码、修复只针对根因、测试按用户行为命名如"取消已支付订单后收到退款"，不写验收编号、凭据不入库）。worker 按落地方式把验收测试和代码一起写（需要的测试设施先按方案搭好，方案没定的新依赖先问用户），新增逻辑按项目惯例补单测。

## 3. 自测

合并各任务后，交给 worker 按 acceptance.md 逐条验证，结果写到 `.devflow/<需求>/selftest.md`（每条：通过/未通过 + 证据 + 对应的用例）：

- 自动化的跑对应用例；人工的实际运行应用走一遍，界面类截图后与 design.html 对照（手段见 SKILL.md「验证手段」）。用户亲验的条目，能在本地或测试环境模拟的先走一遍，走不了的在 selftest.md 注明。
- 另跑项目常规检查：单测、构建、lint、类型检查。

未通过的回到实现修复，不带着已知问题进入 review。

## 4. Code review

按 `references/review-loop.md` 执行。给 reviewer：产品方案、技术方案、设计方案、验收标准、完整 diff、selftest.md。diff 不大时可以按维度并行派多个 reviewer（逻辑正确性与安全、与方案一致性、UI 还原度）；大时按 `references/review-loop.md`「改动大时拆组」。审查要点：

- 正确性、安全性、边界与异常处理。
- 与方案是否一致；偏离方案的地方是否合理并已同步更新方案。
- 是否是最简单直接的实现，有无打补丁、绕路、过度抽象、重复代码。
- 与现有代码风格和架构是否一致，是否便于后续维护。
- 验收测试是否按落地方式写了，是否真的验证了编号描述的可观察结果、是否按用户行为命名（造假的情形见 `references/review-loop.md`「严重度」）。
- 自测结论是否可信：负责跑测试的 reviewer 复跑；它确实跑不了时，由主 agent 或另派一个非作者的 worker 跑，把完整输出交给 reviewer。

## 5. 文档整合（与代码同一个 PR）

代码 review 通过后，把本次的过程文档合并进项目文档：

- **找到项目已有的文档结构**：产品文档、技术/架构文档、设计文档分别在哪（常见位置：`docs/`、`doc/`、wiki 目录、各模块 README）。把本次方案中对理解现状有长期价值的内容合并进对应文档，不原样搬运过程文档。项目没有对应文档、且这部分信息确实需要长期保留时，建最小结构。
- **全盘审查**：更新某份文档时通读整份，删掉与现状不符、重复、过时的内容。文档只描述系统现状，不写历史。
- **README**：只保留项目当前现状的精简介绍和使用说明，不写开发过程、迭代历史、"本次新增了什么"。
- **CHANGELOG**：按项目已有格式加一条，面向使用者描述变化。
- 文档改动同样走一次「做 / 审」，reviewer 重点看：是否与代码现状一致、是否精简、是否残留过程性描述或过时内容。

## 6. 提交 PR/MR

- 按项目已有的提交规范写 commit message。
- 根据仓库的 remote 和本机已有的工具判断怎么提交；判断不了时问用户。
- PR 描述：改了什么、为什么、如何验证（按用户行为列出验证项和结果）、风险与回滚方式；不贴过程讨论。在已有 PR/MR 上做的按第 1 节，不改写描述。
- PR 链接登记到 state.md，进入阶段 4。
