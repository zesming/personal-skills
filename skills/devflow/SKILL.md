# devflow

被委派执行子任务的 subagent 不使用本 skill，直接按 brief 完成任务。

按「角色分工」从当前环境选择 explorer、worker 和 reviewer，brief 写明职责和权限。没有对应角色时使用通用 subagent。同一任务的后续工作优先续用原 subagent；无法续用时，带上必要上下文重新派发。

`references/…` 和 `assets/…` 均相对本 skill 根目录。

## 核心原则

以下原则适用于所有阶段，也用于判断本文件未覆盖的情况：

- **从问题出发，走最短路径**：选择直接、简洁且可维护的方案，尊重现有设计。避免补丁式修复、绕路和无关细节；发现方向不对时回到问题本身重想。
- **在交付边界「做 / 审」**：产品方案、实现方案和代码（含测试、文档）交付下一环节前，都要通过独立的对抗式审查，见 `references/review-loop.md`。草稿和中间文件由作者自检。合入前必须审查 PR 的最终状态：审查后净 diff 有变化，按改动类型补审；影响验收条目的改动要重新取证并补验收审查；无冲突地同步主干只需重跑回归。
- **先确定验收方式**：每份方案写清自己的验收方式并一同审查：产品方案定义 AC，设计方案定义 D，技术方案确定 AC、D 的落地方式并补充 T。开发与回归使用同一组编号。改动越小，记录越精简；按实际情况验收。
- **主 agent 负责端到端结果**：负责分档、与用户沟通、集成和最终验收。方案、实现和自测等依赖共享上下文的连续工作默认自己完成；仅把可并行的独立分支、大量临时输出的调查、独立审查或独立备选方案委派出去。brief 必须完整、自包含。
- **避免绑定外部工具**：使用本地环境、项目自带工具链和用户明确指定的工具，不擅自引入未获用户提出的第三方服务、外部 agent 或新依赖；agent 环境自带的联网检索可用于外部调研，验证工具见「验证手段」。用户已启用或仓库自带的领域/规范类 skill 可遵循，但负责分支、审查或合入的流程编排类 skill（如 project-audit 或其他开发流）不得接管本流程的关卡。

## 第一步：接续或分档

先检查用户原仓库根目录下是否有 `.devflow/*/state.md`。当前位于工作树时，`git worktree list` 第一条是原仓库。若有与本次请求相关的进行中需求，读取其状态并从记录的阶段继续。

没有可接续的需求时，读完请求并快速了解相关代码，判断档位，用一两句话告知用户档位和理由（用户可以调整）：

| 档位 | 适用情况 | 阶段 |
|---|---|---|
| 完整 | 新功能、跨模块改动、改对外接口或数据结构，以及不满足精简条件的 UI 或交互改动 | 1 → 2 → 3 → 4 → 5 |
| 精简 | bug 修复、局部改动、需求明确的小功能；局部 UI 调整仅在**同时满足**以下条件时可用（含视觉自检）：不新增页面或流程、不引入新交互模式或视觉方向、复用现有组件与设计 tokens、用户未要求先出设计方案 | 见「精简流程」 |
| 批量修复 | 按已有问题清单修复，如项目审查报告或 issue 列表 | 见「批量修复」 |

无歧义、低风险的文案、配置、单行等微小改动不进入本流程：直接修改并验证，汇报时附 diff 和验证结果。涉及安全、权限、数据、对外接口、发布或 CI 配置的改动，即使只有一行，也走精简流程。拿不准时选高一档；明显的小事不为凑流程升档。

### 精简流程

1. 定位根因并写明修复思路：改什么、为何是根因、如何验证（复现用例、相关测试、需人工或用户确认的点）。将思路与 diff 一起送 code review，重点检查是否只治表面。根因不确定或影响面较大时，先单独审修复思路。
2. 按 `references/stage3-build.md` 第 1、2 节准备分支并实现。需要补复现用例时，先写用例再修复。按该文件第 5 节更新受影响的文档和 CHANGELOG。运行相关回归（除非影响面广，无需全量 e2e），完成需人工确认的检查；涉及 UI 时按 stage3 第 3 节截图并逐张打开自检，再把结果、截图路径和 diff 一起送 code review，直到没有 must fix。
3. 按 `references/stage3-build.md` 第 6 节提 PR/MR。合入前须满足以下条件，并按 `references/stage4-verify.md` 第 5 节的确认与合入方式征求用户确认（可在同一次询问中请用户完成亲验并决定是否合入；合入或用户放弃后按 `references/stage5-close.md` 收尾）：
   - [ ] CI 全部通过；仓库没有 CI 时注明，并以第 2 步的相关回归为准。
   - [ ] 最终提交上的第 2 步相关回归与人工/视觉检查通过；主干原有失败只有在用户确认可忽略时例外。
   - [ ] 最后一轮 code review 无 must fix，之后没有未审改动。若为自审，如实标明此项不满足；事先授权不适用，由用户审阅后当场决定是否合入。
   - [ ] 分支是最新的，且与目标分支无冲突。
   - [ ] 受影响的文档和 CHANGELOG 已随 PR 更新。
   - [ ] 目标分支保护规则允许合入，包括所需 approval。
   - [ ] 第 1 步列出的用户确认项已由用户确认。

需求有歧义时，先按阶段 1 第 2 节与用户澄清，问题要少而聚焦。

### 批量修复

适用于按项目审查报告、issue 列表等已有问题清单逐项修复的场景。进入该档位时先读取 `references/batch-fix.md`，按其中流程、批次审查和清单修复约定执行；全部批次完成后进入阶段 4 和 5。

## 阶段总览

每个阶段开始时先读对应 reference，并按其中要求执行：

| 阶段 | Reference | 主要产出 |
|---|---|---|
| 1 产品方案 | `references/stage1-product.md` | 产品方案、用户验收用例（AC）与验收前提；涉及 UI 时含交互原型 |
| 2 实现方案 | `references/stage2-design.md` | 技术方案（含验收落地、技术验收 T）；涉及 UI 时含设计方案、设计稿和设计验收 D |
| 3 开发 | `references/stage3-build.md` | 自测和 code review 通过的代码与验收测试、更新后的项目文档、PR/MR |
| 4 回归与合入 | `references/stage4-verify.md` | 测试集治理、全量回归、验收审查；经用户确认后合入 |
| 5 收尾 | `references/stage5-close.md` | 清理临时资源并移除工作目录 |

用户从中间阶段开始（如“方案已经有了，直接开发”），先确认已有前置产物是否完整够用；只补缺项，不从头重做。

在已授权范围内自动推进，直到完成本次约定的交付。常规细节可按合理、可逆的假设推进，记录影响结果的假设。遇到以下情形，暂停相关工作，请用户决定：

- 有必须由用户拍板的问题，如需求歧义、实质取舍或缺少外部信息；或需要引入新依赖。
- 环境无法派出独立 reviewer，见 `references/review-loop.md`。
- 「做 / 审」、自测或回归修复连续几轮无进展，复盘后仍需用户判断，见 `references/review-loop.md`。
- 合入主干前，必须按 stage4 第 5 节征求用户确认。
- 将执行不可逆或影响他人的操作，如删除非本流程创建的资源、force push 或修改共享配置。

等待答复时，继续与该决定无关且已获授权的工作。只能同步提问时，先做可独立推进的工作，再集中提问。

结束前逐项核对约定交付和适用验收，说明未完成或未验证的事项。用户中止流程时，按阶段 5 收尾。

## 角色分工

| 角色 | 职责 |
|---|---|
| explorer | 并行独立调查、大量临时输出的检索或外部调研；只读，结论须附出处并区分已验证事实、推断和未知。仅定位代码时可用专门的检索角色。 |
| worker | 编写代码、测试和文档，制作 HTML 原型或设计稿。 |
| reviewer | 独立审查交付关卡的产出；只读，可运行测试。 |

产品方案、技术方案和设计说明由主 agent 编写。要挑战关键假设时，派干净上下文的 reviewer。需要独立备选方案时，用自包含 brief 派只读 subagent，由主 agent 取舍。方案依赖大量对话背景时才继承上下文，并考虑已有思路对备选方向的影响。修改由原作者继续完成。环境无法派 subagent 时，主 agent 承担其他角色的工作，独立审查按 `references/review-loop.md` 处理。

## 工作目录与状态

完整、精简和批量修复档位都在用户原仓库根目录建立 `.devflow/<需求简名>/`，不要放进本流程创建的工作树（删除工作树会连同目录一起删除）。过程产物不入库。若 `git rev-parse --git-path info/exclude` 指向的文件尚未忽略 `.devflow/`，只追加该规则；不改已有规则或项目 `.gitignore`。

建好工作目录并追加忽略规则后，将资源基线写入 `.devflow/<需求>/baseline.txt`：模拟器/模拟机列表（按项目平台使用 `xcrun simctl list devices`、`emulator -list-avds`、`adb devices`、`hdc list targets` 等）、监听端口、已有工作树（`git worktree list`）、`/tmp` 顶层条目、原仓库当前分支和 `git status --short`。macOS 的 `$TMPDIR` 常有大量条目，不做目录基线；凡向其中写入的资源都登记具体路径。

按 `assets/templates/state.md` 创建 `state.md`（按实际情况填写占位），每次阶段推进或循环结束后原地更新。它是供接续工作的当前快照，不按时间追加。命令输出、测试计数和排查过程写入相应产物（如 `selftest.md`、`regression.md`）或独立记录；状态只写结论和文件位置。用户决策、审查记录、本流程创建的资源按清单增删。使用与用户沟通相同的语言和完整句子，不堆缩写。

在主要阶段边界（如阶段 2→3、3→4）更新 `state.md` 时，确保关键入口、已锁定决策和下一步足以支持冷启动接续。若当前会话上下文已经较重，可建议用户新开会话继续（如“继续 devflow <需求简名>”），由用户决定，不强制中断。

验收编号（AC、D、T）只用于 `.devflow/`，不写入代码、测试名、提交信息、PR 描述或项目文档，避免工作目录删除后留下悬空编号。问题清单自带的编号不受此限。

创建资源后立即登记在 `state.md`「本流程创建的资源」中。收到 subagent 的结果后，也要登记其列出的资源。

## 委派 subagent

brief 必须自包含，写明目标、范围（做什么和不做什么）、约束、输入文件的绝对路径（包括本 skill 模板）、输出位置和验收标准；要求返回时列出创建的临时文件、工作树、进程和模拟器。代码位于另一个工作树时，写明工作树绝对路径与分支。

- 自包含任务用干净上下文和 brief。依赖大量对话背景时可继承上下文，环境不支持继承时补全 brief。新派 reviewer 必须从干净上下文开始，只接收审查所需材料。环境允许选择时，显式选择不继承会话。同一任务的后续工作优先续用原 subagent。
- 每份 brief 都注明“不要启用 devflow skill”，避免 subagent 在子任务内递归触发主流程与关卡编排。
- 给 reviewer 和其他只读 subagent 的 brief 明确写：“只读：不修改文件，不执行会改变工作区或外部状态的命令（运行测试除外）。”不要假设 agent 定义中的只读沙箱一定生效。
- git 写操作、push、提 PR、合入、联网安装依赖、启动服务或模拟器等较高权限操作，只有确认执行环境允许时才委派；否则主 agent 自己执行。遇到沙箱或权限拒绝，如实报告，不绕路。
- 并行写入时分配不重叠的文件范围；环境支持原生 worktree 隔离时优先启用，将其创建的工作树和分支登记到 `state.md`「本流程创建的资源」供阶段 5 清理，并由主 agent 统一集成。
- 环境允许为 subagent 指定模型或推理档位时，explorer 和纯代码定位任务可用更轻快的模型；reviewer、根因分析和方案设计保持完整能力。
- 需运行测试、启动服务或模拟器的任务不要在同一工作区并行，以免争抢端口或构建目录；并行 reviewer 中只允许一个运行测试，其余只读审查。
- 核验 subagent 的结论：抽查关键事实；若它声称测试通过，查看测试输出。

## 验证手段

运行应用、截图、走用户旅程或做视觉对照时，使用当前环境可用的可靠验证工具：项目测试工具链和脚本、本机 headless 浏览器或模拟器命令行、agent 环境自带的浏览器、截图或 computer-use 工具。无需先征求用户同意。

- 只在本地或测试环境验证，不用真实用户账号或生产数据执行有副作用的操作。
- 不为验证新装依赖；确实需要时先征求用户同意。
- subagent 没有验证工具时由主 agent 验证；若环境都没有可用手段，再请用户协助。

## 与用户沟通

- 默认使用中文。
- 提问前先形成整体思路，集中询问真正影响结果的问题，建议不超过 5 个。按影响排序，每题给具体选项和推荐项，并说明不同选择的后果。能从代码、文档或调研得出的不问；可以合理默认的写入“假设”。
- 阶段完成时用几句话汇报产物位置、关键决策、审查轮次和遗留风险，不在对话中粘贴整份文档。
