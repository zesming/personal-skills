# devflow

被委派执行子任务的 subagent 不使用本 skill，直接完成 brief 里的任务。

本 skill 同时用于 Claude Code 和 Codex。文中的 explorer / designer / worker / reviewer 指角色，不是 agent 名字：派发时按「角色分工」里的描述，从当前环境里选最匹配的 subagent；没有合适的就用通用 subagent，并把角色要求（尤其是只读）写进 brief。续用已有 subagent 的方式：Claude Code 用 SendMessage，Codex 用 followup_task；有的 subagent 不支持续用，需要追问时重新派一个。派 reviewer 时不让它继承当前对话（Codex 中一律用 `fork_turns="none"`），保证它拿不到作者的思路。

文中的 `references/…`、`assets/…` 都相对本 skill 根目录。

## 核心原则

这些原则适用于所有阶段；本文件没覆盖的情况也按它们判断：

- **第一性原理，最短路径**：从真实问题出发，选最直接、最简洁的做法；尊重已有设计，顾及可维护性；不打补丁、不绕路、不在细枝末节上钻牛角尖。方向不对时回到问题本身重想，不在错误方案上叠加。
- **最小执行单元是「做 / 审」**：任何产出（文档、原型、代码、测试、文档更新）交付前都要经过独立的对抗式审查，规则见 `references/review-loop.md`。合入前 PR 的最终状态必须审过：最后一次审查后 PR 净 diff 又有变化的，按改动类型补审，影响验收条目的重新取证并补验收审查；无冲突地同步主干只重跑回归。
- **做之前先定怎么验**：每份方案带上自己的验收方式一起审（产品方案 AC、设计方案 D，技术方案定它们的落地并补 T），开发和回归按同一套编号兑现。档位越小写得越少，有什么验什么。
- **主 agent 是 PMO**：负责分档、拆解、委派、汇总、校验结果和与用户沟通；具体产出交给 subagent，小到不值得委派的自己做。
- **不耦合外部工具**：只用本地环境、项目自带工具链和用户明确指定的工具，不擅自引入用户没提的第三方服务、其他 skill 或外部 agent。agent 环境自带的联网检索（外部调研用）和验证工具（见「验证手段」）可以直接用。

## 第一步：接续或分档

先看用户原仓库根目录下有没有 `.devflow/*/state.md`（当前在工作树里时，`git worktree list` 的第一条就是原仓库）：有与本次请求相关的进行中需求，就读取它，从记录的阶段接着做。

否则读完请求、快速了解相关代码，判断档位，用一两句话告诉用户档位和理由（用户可以改）：

| 档位 | 什么情况 | 走哪些阶段 |
|---|---|---|
| 完整 | 新功能、跨模块改动、涉及 UI/交互、改对外接口或数据结构 | 1 → 2 → 3 → 4 → 5 |
| 精简 | bugfix、局部改动、需求明确的小功能 | 见下方「精简流程」 |
| 微小 | 改文案、改配置、单行修改，需求无歧义 | 按精简流程，但不建工作目录和 state.md，修复思路随 diff 一起审；收尾清理验证时启动的资源，合入后删本流程建的分支 |
| 批量修复 | 按一份已有的问题清单修复（项目审查报告、issue 列表） | 见下方「批量修复」 |

拿不准时往上一档靠；明显的小事不要为了"流程完整"升档。

### 精简流程

1. 定位根因，写出修复思路（改哪里、为什么这是根因、怎么验证：复现用例、要跑的相关测试、需要人工或用户确认的点），交 reviewer 审，重点看是否治标不治本。
2. 按 `references/stage3-build.md` 第 1 节切分支。能写复现问题的测试就先写，再修复；受影响的文档/CHANGELOG 按该文件第 5 节同步更新。跑与改动相关的回归测试（不要求全量 e2e，除非改动影响面广），走一遍需要人工确认的点，结果连同 diff 一起进 code review，循环到无 must fix。
3. 提 PR/MR（stage3 第 6 节）。合入前按 `references/stage4-verify.md` 第 5 节问用户，其中"本地全量回归"用第 2 步的相关回归代替，"验收审查"由第 2 步的 code review 承担，用户亲验即第 1 步列出的需要用户确认的点。合入或用户放弃合入后，按 `references/stage5-close.md` 清理。

需求本身有歧义时，先按阶段 1 第 2 节与用户澄清（问题更少、更聚焦）。

### 批量修复

1. 清单自带修复约定的，其中的分支、提交格式、推送与同步、进度记法、合入前条件按约定执行，与本 skill 冲突时这几项以约定为准（合入前条件是在 stage4 第 5 节之外追加，两者都要满足）；合入确认和不可逆操作仍按本 skill 问用户。指定的 PR/MR 已合入或关闭时先问用户。
2. 先核实条目在当前代码上仍成立；不成立、或与项目约定冲突的，带证据按约定处理或交用户决定。清单里标为待决的条目（待确认、存在分歧等），先集中问用户再动手。
3. 条目的描述和修复建议就是需求，条目编号代替 AC 编号，不写 product.md。多数条目按精简流程第 1–2 步做，全部条目共用一个分支和 PR/MR（stage3 第 1 节）；清单已经质证过的，修复思路随 code review 一起审，不单独审。改产品行为或跨模块的条目补技术方案后再做。
4. 按模块或条目分批实施。每批的 diff 相对上一批审完的提交（第一批相对开始时的分支头）；同步目标分支只在两批之间做，合并提交作为下一批的起点，有冲突解决的单独交审。本地可以按条目提交；每批 code review 无 must fix（改动大时按 `references/review-loop.md`「改动大时拆组」）后再推送。进度按约定记（报告状态、PR/MR 勾选），没有约定时记在工作目录的 `progress.md`，进度的更新随下一批一起审；每批的验证结果、需要用户确认的点和审查记录都记在 `review.md`，state.md 只记批次和指向。
5. 全部批次完成后，对 PR/MR 的净 diff 按「改动大时拆组」派一次衔接 reviewer（有 must fix 照常循环：修复交对应组的 reviewer 审，衔接再复核），再按阶段 4 回归与合入、阶段 5 收尾。各批 code review 审过的测试不再重审，阶段 4 第 1 节新增或删改的用例由第 3 节验收审查审，其输入见该节，用户亲验即 review.md 记下的需要用户确认的点。

## 阶段总览

每个阶段开始时先读对应的 reference，按它执行：

| 阶段 | 文件 | 产出 |
|---|---|---|
| 1 产品方案 | `references/stage1-product.md` | 产品方案、交互原型（涉及 UI 时）、用户验收用例（AC）及验收前提 |
| 2 实现方案 | `references/stage2-design.md` | 技术方案（含验收落地、技术验收 T）、设计方案与设计稿（涉及 UI 时，含设计验收 D） |
| 3 开发 | `references/stage3-build.md` | 通过自测和 code review 的代码与验收测试 + 已更新的项目文档，提交 PR/MR |
| 4 回归与合入 | `references/stage4-verify.md` | 测试集治理完毕、全量回归全绿、验收审查通过，经用户确认后合入 |
| 5 收尾 | `references/stage5-close.md` | 临时产物与模拟器清理干净，工作目录移除 |

用户从中间阶段进入（如"方案已经有了，直接开发"）时，先确认前置产物存在且够用，缺什么补什么，不从头重来。

阶段之间自动推进，不用每步等用户批准；只在这些情况停下来找用户：
- 有必须由用户拍板的问题（需求歧义、实质取舍、引入新依赖、外部信息缺失）；
- 环境派不出独立的 reviewer（见 `references/review-loop.md`），停下等用户决定；
- 「做 / 审」、自测或回归修复连续几轮没有进展，复盘后仍需用户判断（见 `references/review-loop.md`）；
- 合入主干前（必须有用户确认，规则见 stage4 第 5 节）；
- 要执行不可逆或影响他人的操作（删除非本流程创建的资源、force push、改共享配置等）。

用户中途中止时，按阶段 5 收尾。

## 角色分工

| 角色 | 做什么 |
|---|---|
| explorer | 检索本地代码与文档、做外部调研，返回带出处的结论。只读。边界明确的小检查，可用环境里更轻量的检索 agent（有的话） |
| designer | 产出产品方案、技术方案、设计说明的正文。只读：返回文本，由主 agent 原样写入 `.devflow/` 下的文件 |
| worker | 写代码、测试、文档；制作 HTML 原型和设计稿 |
| reviewer | 独立审查任何产出。只读，可以跑测试 |

修改时续用原作者：designer 返回修订后的正文，主 agent 覆盖写入；worker 直接改文件。reviewer 每轮新派（见 `references/review-loop.md`）。环境派不出 subagent 时，其他角色的工作由主 agent 自己做，审查按 review-loop.md 处理。

## 工作目录与状态

完整、精简和批量修复档位在用户原仓库根目录建工作目录 `.devflow/<需求简名>/`（不放进本流程建的工作树：删工作树会连它一起删掉），过程产物都放这里，不入库：`git rev-parse --git-path info/exclude` 指向的文件还没忽略 `.devflow/` 时追加这条规则，不动已有规则，不改项目的 `.gitignore`。

建好工作目录、追加忽略规则后，把资源基线记到 `.devflow/<需求>/baseline.txt`：模拟器/模拟机列表（按项目平台用 `xcrun simctl list devices`、`emulator -list-avds` / `adb devices`、`hdc list targets` 等）、监听中的端口、已有的 git 工作树（`git worktree list`）、`/tmp` 顶层条目、原仓库的当前分支和 `git status --short`。`$TMPDIR`（macOS 上是 `/var/folders/…/T/`，很多工具默认写这里）条目太多不做基线，凡是往里写的东西都按具体路径登记。

`state.md` 按 `assets/templates/state.md` 的格式建（条目是示例，按实际填写），每次阶段推进或循环结束后更新。它是给接续看的当前快照：原地改写，不按时间往下追加；命令输出、测试计数、排查经过写进对应的产出文件（selftest.md、regression.md 等）或单独的记录文件，state.md 只留结论和文件指向。用户决策、未采纳的建议、本流程创建的资源这几节是清单，按条目增删。用与用户沟通的语言、写给人看的完整句子，不压缩成缩写串。

验收编号（AC、D、T）只在 `.devflow/` 内使用，不写进代码、测试名、提交信息、PR 描述和项目文档（工作目录删除后会悬空）；问题清单自带的编号不受此限。

创建资源时立刻登记到 state.md「本流程创建的资源」；subagent 返回中列出的资源，主 agent 收到后登记。

## 委派 subagent

brief 要自包含：目标、范围（做什么/不做什么）、约束、输入文件（含本 skill 的模板）的绝对路径、输出位置、验收标准，并要求返回时列出它创建的临时文件、工作树、启动的进程和模拟器。代码在另一个工作树里时，brief 写明工作树的绝对路径和分支。

- 每个 brief 都注明"不要启用 devflow skill"。
- 给 designer 和 reviewer 的 brief 写明"只读：不修改文件，不执行会改动工作区或外部状态的命令（运行测试除外）"。不依赖 agent 定义里的只读沙箱，它不一定生效。
- git 写操作、push / 提 PR / 合入、联网安装依赖、启动服务或模拟器这类需要较高权限的操作，确认执行者的环境允许再委派，否则主 agent 自己做；被沙箱或权限拒绝时如实报告，不绕路。
- 并行写入时划分不重叠的文件范围。
- 要跑测试、启动服务或模拟器的任务不在同一工作区并行（会抢端口和构建目录）；并行的 reviewer 只让一个跑测试，其余只读审查。
- 校验 subagent 的结论：抽查关键事实，声称通过的测试自己看输出。

## 验证手段

运行应用、截图、走用户旅程、做视觉对照时，直接用当前环境里可用的验证工具：项目自带的测试工具链和脚本、本机的 headless 浏览器或模拟器命令行、agent 环境自带的浏览器/截图/computer-use 类工具。选能可靠复现、能留证据的，不用先问用户。这些工具只用于验证，并且：

- 在本地或测试环境里验证，不用用户的真实账号或生产数据做有副作用的操作。
- 不为验证新装依赖，确实需要时先问用户。
- subagent 的环境里没有这些工具时，由主 agent 自己验证；都没有可用手段时再问用户。

## 与用户沟通

- 默认用中文。
- 提问前先形成自己的整体思路，再集中讨论真正不确定的点：问题建议控制在 5 个左右，按影响排序，每个给具体选项和推荐项，说明不同选择的后果。能从代码、文档或调研得出的不问；能合理默认的写成"假设"。
- 阶段完成时用几行话汇报：产出在哪、关键决策、审查轮次、遗留风险；不把整份文档贴进对话。
