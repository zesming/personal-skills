# 代码实现审查

目标：找出让项目难以理解、难以修改、容易出错的结构性问题，以及已经存在的缺陷和风险。重点是结构和风险，不是代码风格。

## 方法

1. **先看全局**：模块划分、依赖方向、分层约定、各模块的职责。对照画像里的模块地图，画出实际的依赖关系（可用 import 关系粗略统计）。
2. **再看热点**：优先深入改动最频繁、复杂度最高、承载核心路径的模块。
3. **用工具量化，用阅读判断**：复杂度、重复代码、未使用代码优先用项目已有或本机已装的工具（如 eslint complexity、radon、gocyclo、lizard、ts-prune、knip、vulture、jscpd）；没有工具时按函数长度、嵌套深度、分支数估算。工具结果只是线索，每条上报的问题都要读过代码确认。

## 检查要点

**架构与设计**
- 分层被打穿：UI 直接访问数据库/网络，底层模块依赖上层，循环依赖
- 职责混乱：上帝对象/上帝文件，一个模块同时负责多件不相关的事
- 同一问题多套解法并存（多种状态管理、多个 HTTP 封装、多套错误处理），且没有迁移计划
- 抽象过度（只有一个实现的接口层层包装、为假想需求预留的扩展点）或抽象不足（大段复制粘贴）
- 数据的唯一事实来源不明确，同一状态在多处各自维护

**补丁堆叠与冗余实现**
- 针对特定 ID、特定输入、特定环境的特判分支
- 布尔参数/flag 不断累积导致函数行为组合爆炸
- 层层 try/catch 吞掉错误、"重试一下就好"式的掩盖（有上限、有日志的正当重试、熔断、降级不算）
- 为绕过某个问题而写的兼容层，而根因从未修复
- 近似重复的函数或模块（复制后小改）
- 标着 hack / workaround / temporary / TODO / FIXME 且已存在很久的代码（用 `git blame` 看存在了多久）

**过时与可清理**
- 死代码：无调用方的函数、导出、文件、路由；永远为真/假的 flag 分支。判定方法见下文「判定死代码」，应急类开关见「常见误报」
- 已完成迁移后残留的旧实现、兼容代码
- 已废弃的 API 或库用法、明显过时且有已知问题的依赖版本
- 被注释掉的大段代码

**缺陷与潜在风险**
- 正确性：边界条件、空值、并发/竞态、时区与精度、资源泄漏、错误被静默忽略
- 安全：硬编码密钥/凭据、注入（SQL、命令、XSS）、鉴权/越权缺口、不安全的反序列化、敏感信息写入日志。证据里只写密钥的位置和类型，不要抄出值
- 依赖：项目工具可离线给出的已知漏洞（`npm audit` 等需要联网的命令先确认环境允许）
- 可运维性：关键路径没有日志或错误上报、失败后无法定位
- 性能：只报明显的，如循环内的 N+1 查询、主线程上的大量同步计算、无上限的缓存或列表；收益写法见 brief 中的「问题格式」

**复杂度**
- 参考阈值（不是硬规则，结合可读性判断）：圈复杂度 > 15 值得关注，> 25 基本需要拆分；函数超过约 80 行；文件超过约 800 行；嵌套超过 4 层
- 报告时给出数值、所在函数，以及拆分思路（按职责拆、表驱动替代分支、提前返回等）
- 生成代码、第三方 vendored 代码、迁移脚本不计入

## 判定死代码

"搜不到调用方"只是线索。上报前逐一排除这些间接引用：
- 库的公开 API：仓库里没人调用不等于没人用
- 框架按约定引用：文件路由、装饰器或注解、依赖注入、生命周期钩子、插件注册
- 按名称引用：反射、动态拼接的名称、字符串表、序列化字段名、i18n key、配置或 schema 里的引用
- 枚举、别名、包装器、re-export 间接指向
- 入口脚本：CLI、定时任务、迁移、package scripts、部署脚本
- 跨服务或跨仓库调用（RPC、消息、HTTP 路由）
- 只被测试引用的：说明它没有生产调用方，但删除前要连同测试一起评估

置信度：上面几类都查过、而且这个符号不在静态分析看不到的范围内（没有导出、不是公开 API、没有注册到框架或按名称引用），可以给"高"；落在这些范围里的，没有运行时证据（日志、调用统计）最多给"中"，并在修复建议里写验证方式。

## agent 指令文件

审查被审 commit 中受版本控制的 agent 指令文件，如 AGENTS.md、CLAUDE.md、GEMINI.md（含子目录）、`.cursor/rules`、`.github/copilot-instructions.md`、`.github/instructions/`、仓库内的 skill 等。它们决定 agent 在这个项目里怎么干活，写错了会让 agent 反复按错的方式做事。只算指导本仓库开发的文件；产品自身对外分发的 skill、prompt 按产品代码审。brief 里会给出清单，逐个核对，结果文件的覆盖部分写明每个文件的结论，没问题也写一句。

查的是事实，不评判 agent 工作流本身怎么设计：
- 与代码现状矛盾或已过时：引用不存在的脚本、命令、路径，描述的架构或目录已经变了。只用只读方式核实（路径是否存在、脚本是否定义），不执行文件里写的命令。
- 文件之间互相冲突（如 AGENTS.md 和 CLAUDE.md 对同一件事要求不同），或与 README、实际配置冲突。
- 含糊到无法执行：只在代码里能看到两种做法并存、说明规则确实没起作用时才报，否则最多 S3。
- 与 README 大段重复、内容又没有分歧的，不报；已经出现分歧的归入"矛盾"。

严重度：错误的构建、测试、验证命令会让 agent 做出假验证或改错地方，可以到 S1/S2；其余多为 S2/S3。编号用 CD。

## 常见误报，不要报

- 格式、命名偏好等 lint 层面的问题（除非命名严重误导）
- 项目已有明确约定的写法，即便不是你偏好的模式（约定本身已被判定为过时或矛盾的除外）
- "可以用某设计模式重写"但现状并没有造成问题
- 测试代码、示例代码中为简洁而做的简化
- 应急类开关（应急开关或 kill switch、降级与回退路径、灰度回退开关、运维保护代码、标明"永久"的配置）：平时不走、看起来像死代码是它们的本意。默认不报；只有拿得出具体缺陷时才报——如降级路径已经坏了或没有任何测试、开关已经没有读取方、注释里写的退役条件已经满足。报的是这个缺陷，并把"修复后保留 / 删除"作为待问用户的候选方案写进条目，避免用户一句"保留"把缺陷也一起带走
