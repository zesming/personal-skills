# 产品逻辑审查

目标：判断产品是否用最少的功能、最短的路径实现了它声称的目标；找出冗余、断裂和自相矛盾的地方，给出精简方案。

## 方法

1. **还原产品意图**：从 README、文档、落地页/首页文案、应用内引导文案归纳"这个产品为谁解决什么问题"。意图写不清楚本身就是一条发现。
2. **列功能清单**：从路由、页面、菜单、命令、API 端点、配置项、feature flag 中归纳全部功能，每项标注它服务于哪个目标。对不上任何目标的，进入冗余候选；看不出意图、需要业务信息才能判断的，在条目里写"待问用户"（见 brief 中的「问题格式」），不要猜。
3. **走核心路径**：对画像中的每条核心用户路径，按代码（必要时实际操作）一步步走，记录步数、每步需要用户输入或决策什么、出错时去哪。
4. **找矛盾**：对照文案、文档、代码行为和数据模型，看它们讲的是不是同一件事。

## 检查要点

**冗余与可精简**
- 同一件事有两种以上做法（两个入口、两套设置、新旧两版流程并存）
- 与核心目标无关、或只服务极少场景却占据显著位置的功能
- 做了一半的功能：入口隐藏、flag 常关、没有任何调用方、文档已不提。应急类开关除外（见「常见误报」）；判断"没有调用方"前，先按 code.md（brief 中给出路径）「判定死代码」一节排除间接引用（API 端点尤其容易误判）
- 暴露给用户的配置项过多，其中大部分有合理默认值即可
- 概念过多：用户需要理解的名词、对象、状态超出完成任务的必要

**用户路径**
- 完成核心任务的步数明显多于必要；必经步骤里有可以推迟或省略的（过早要求注册、填写非必要信息）
- 死路：某一步之后无法继续、无法返回、出错后没有恢复路径
- 首次使用：新用户能否在不读文档的情况下完成第一个核心任务
- 状态之间的跳转是否完整（创建 → 编辑 → 删除 → 恢复；成功 / 失败 / 处理中）

**逻辑一致性**
- 业务规则在不同入口下表现不同（如同一操作在列表页和详情页限制不同）
- 状态机缺失或冲突：存在不可达状态、无法离开的状态、文案与实际状态不符
- 权限、计费、配额等规则自相矛盾，或前后端判定不一致
- 文档、帮助文案描述的行为与实际行为不符
- 命名与含义不符（叫"删除"实际是"归档"等）

**无界面项目**（库、CLI、服务）：把"用户路径"换成"调用方完成典型任务的路径"——最小可用示例要几步、默认值是否合理、错误信息能否指导下一步、命令/参数/接口命名是否一致、是否存在同功能的多个接口。

## 常见误报，不要报

- 只因为"我会这么设计"而不同的做法；要说明现做法造成了什么具体问题
- 明显服务于特定用户群体或合规要求的功能，在没有证据时判定为冗余——可以记 S3 并给出验证方式
- 已在文档或 issue 中说明了取舍理由的设计，除非理由已不成立
- 应急类开关（应急开关或 kill switch、降级与回退路径、灰度回退开关、运维保护代码、标明"永久"的配置）：平时用不到是本意。默认不报；拿得出具体缺陷（入口已经失效、没有任何验证）时才报，并把"修复后保留 / 删除"作为待问用户的候选方案

## 额外产出

除问题清单外，给一段"精简建议汇总"：建议删除、合并、降级（移到次要位置）的功能各有哪些，以及精简后的核心路径长什么样。每项建议都要对应清单里的一个问题编号，这样它和其他问题一起接受质证，报告里只汇总已确认的部分。
