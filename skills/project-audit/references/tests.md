# 测试审查

目标：判断测试是否真的在保护产品的关键行为。覆盖率数字只是线索，关键是"核心路径坏了，测试会不会红"。

## 方法

1. **看基线结果**：主 agent 已跑过的测试结果和覆盖率报告（brief 中给出的 `<AUDIT>/baseline/` 绝对路径）。记录通过/失败/跳过数量、耗时、是否有不稳定用例。测试本身跑不起来就是一条发现。
2. **按风险对照覆盖**：把画像中的核心用户路径和高风险模块（代码维度的热点、复杂模块、涉及金额/权限/数据写入的逻辑）逐一对照，找出哪些测试在保护它们。这比列"覆盖率 < 80% 的文件"有用得多。
3. **抽查测试质量**：对每个测试目录抽样阅读，重点读核心路径相关的测试。
4. **可选的变异验证**：怀疑某个测试是假测试时，在发现里提出候选：哪个测试、破坏哪段实现（`文件:行号` 和具体改法，如删掉某个判断、反转条件）、预期哪些测试应失败。只提候选，不要自己改代码；由主 agent 在汇总阶段执行，结果补进条目的依据。

## 检查要点

**未被覆盖**
- 核心用户路径缺少端到端或集成层面的测试
- 高风险逻辑（金额计算、权限判定、状态转换、数据迁移、并发）缺少单元测试
- 只测了成功路径，没有错误路径、边界值、空输入
- 近期修过的 bug 没有对应的回归测试（看提交历史里的 fix）
- 每条给出：未覆盖的行为、风险、建议补什么层级的测试（单元/集成/e2e）以及大致用例

**过时**
- 测试的是已删除或已改名的功能、已不存在的接口
- 被 skip / xit / `@Ignore` 且没有说明原因，或说明的原因已不成立
- 快照/fixture 与当前实现脱节，大家习惯直接更新快照
- 在 CI 中被排除、实际上从来不运行的测试

**假测试**（通常 S0/S1）
- 没有断言，或断言恒为真（`expect(true)`、只断言"不抛异常"却没有任何异常路径）
- mock 了被测对象本身，或只断言 mock 返回了 mock 设定的值
- 吞掉异常使测试永远通过；断言写在不会执行的回调里
- 为通过而对特定输入特殊处理、放宽断言、硬编码期望为当前（错误的）输出
- 变异验证中破坏实现后依然通过

**无意义的过度测试**（通常 S2/S3）
- 测试语言或框架本身的行为、简单 getter/setter、常量
- 多个测试反复验证同一路径，没有增加信息
- 与实现细节强耦合（断言私有方法调用次数、内部结构），导致正常重构就大面积失败
- 大而全的快照测试，任何改动都会失败却没人认真看
- 每条给出：建议删除、合并还是改写

**测试基础设施**
- 测试之间有隐式依赖、顺序敏感、共享可变状态
- 不稳定用例（依赖真实时间、网络、随机数而未固定）
- 测试运行过慢：以基线实测耗时为依据，指出最慢的用例或套件，以及可能的原因（如缺少 mock、真实等待）

## 常见误报，不要报

- 为追求覆盖率数字而建议给琐碎代码补测试
- 项目有意不测的部分（如纯 UI 布局、自动生成的代码），除非它们承载了逻辑
