# 测试审查

核对测试能否捕获关键回归，并找出可移除、合并或改写的低价值用例。

## 方法

1. **看基线结果**：主 agent 已跑过的测试结果和覆盖率报告（brief 中给出的 `<AUDIT>/baseline/` 绝对路径）。记录通过/失败/跳过数量、耗时、是否有不稳定用例。测试本身跑不起来就是一条发现（审查环境的限制除外，见下）。基线里的失败由测试维度负责全部定性，不推给其他维度；按原因分组：
   - **产品缺陷**：按影响定级；由测试维度报时用 TS 前缀，"维度"里写上产品或代码。
   - **测试缺陷**（fixture、mock、断言跟不上实现，不可移植，不稳定等）：同根因合并成一条，列出用例与归因。在常规入口（项目的默认测试命令，或 CI 调用的测试）里失败的通常 S1——一直红着的基线会让人习惯忽略失败；不在常规入口里的，按它保护的行为的重要性定级。
   - **审查环境的限制**（沙箱、网络、权限，缺本机工具或服务）：有报错依据就只写进报告"局限"。
   - **运行时或工具链版本不兼容**：项目声明了版本（engines、`.nvmrc`、CI 配置等）而审查环境与之不符的，写进"局限"；项目没声明的，作为工程问题评估是否上报。对照证据可以是关闭相关特性或换参数后通过。
2. **按行为对照覆盖**：将核心路径和高风险模块对照到具体用例、断言和入口。用覆盖率辅助定位，按关键行为判断保障是否充分。
3. **抽查测试质量**：对每个测试目录抽样阅读，重点读核心路径相关的测试。
4. **可选的变异验证**：怀疑某个测试是假测试、或要确认某个关键回归没有任何测试能发现时，在发现里提出候选（不用于证明现有测试有效；静态即可证明测试没有产品依赖的，如没有引用任何产品代码，不需要变异）：哪个测试、破坏哪段实现（`文件:行号` 和具体改法，如删掉某个判断、反转条件）、预期哪些测试应失败。只提候选，不要自己改代码；由主 agent 在汇总阶段执行，结果补进条目的依据。

## 检查要点

**未被覆盖**
- 核心用户路径缺少端到端或集成层面的测试
- 高风险逻辑（金额计算、权限判定、状态转换、数据迁移、并发）缺少单元测试
- 只测了成功路径，没有错误路径、边界值、空输入
- 近期修过的 bug 没有对应的回归测试（看提交历史里的 fix）
- 每条给出：未覆盖的行为、风险、建议补什么层级的测试（单元/集成/e2e）以及大致用例

**过时**
- 测试的是已删除或已改名的功能、已不存在的接口
- 被 skip / xit / `@Ignore` 且没有说明原因，或说明的原因已不成立
- 快照/fixture 与当前实现脱节，大家习惯直接更新快照
- 在 CI 中被排除、实际上从来不运行的测试

**假测试**（通常 S0/S1）
- 没有断言，或断言恒为真（`expect(true)`、只断言"不抛异常"却没有任何异常路径）
- mock 了被测对象本身，或只断言 mock 返回了 mock 设定的值
- 吞掉异常使测试永远通过；断言写在不会执行的回调里
- 为通过而对特定输入特殊处理、放宽断言、硬编码期望为当前（错误的）输出
- 变异验证中破坏实现后依然通过

**无意义的过度测试**（通常 S2/S3）
- 测试语言或框架本身的行为、简单 getter/setter、常量
- 多个测试保护同一行为、故障模式和输入边界。对照实际断言以及测试层级能捕获的风险
- 与实现细节强耦合（断言私有方法调用次数、内部结构），导致正常重构就大面积失败
- 大而全的快照测试，任何改动都会失败却没人认真看
- 每条给出删、并或改写建议。仍需保护的行为要指出保留的用例、断言和验证方法。对只验证框架、过时或无产品断言的用例，给出无需承接的证据

**测试基础设施**
- 测试之间有隐式依赖、顺序敏感、共享可变状态
- 不稳定用例（依赖真实时间、网络、随机数而未固定）
- 测试运行过慢：以基线实测耗时为依据，指出最慢的用例或套件，以及可能的原因（如缺少 mock、真实等待）

## 常见误报

- 为追求覆盖率数字而建议给琐碎代码补测试
- 项目有意不测的部分（如纯 UI 布局、自动生成的代码），除非它们承载了逻辑
- 验证同一功能的不同故障模式、平台、数据边界或集成层行为
