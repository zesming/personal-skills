# 提交 PR/MR

PR/MR 是本次审查后所有修复的统一载体：报告是它的第一个提交，之后的修复都追加到同一分支，描述里的清单就是修复进度。

下文 `<AUDIT>`、`<临时路径>` 的含义见 SKILL.md 开头。

## 前置检查

- **授权**：看 progress.md。已授权才推送和开 PR/MR；仍是"待问"就再问一次，没有回答按未授权处理。本地分支和提交无论是否授权都做。
- **平台与目标**：沿用第 1 步记录的 `<推送 remote>`、`<目标 remote>`、可见性、PR/MR 目标分支、被审 commit。第 1 步用户尚未就"含远端没有的提交 / 基线分支远端不存在"做出选择的，不推送。GitHub 用 `gh`，GitLab 用 `glab`，检查认证状态（`gh auth status` / `glab auth status`）。
- **未推送提交**：第 1 步已就"被审 commit 含远端没有的提交"征得用户选择；用户没同意一起推送的，不推。

## 敏感内容

- 报告中所有密钥、凭据、个人数据只写位置和类型，不写值，提交前再搜一遍。
- 要入库的截图逐张检查，含个人数据、token、内部地址的打码或不入库。
- 仓库按公开处理时（第 1 步判定），所有安全类条目的细节（具体位置、利用方式）不进入报告和 PR 描述：报告和 PR 清单里保留占位条目（编号、严重度、"安全类，详情见私下渠道"），照常参与状态跟踪和"S0/S1 全部处理"的判断；细节写在 `<AUDIT>/security.md`，并告诉用户、问是否需要走私下修复渠道。
- **推送前确认**：有公开风险时——仓库按公开处理、PR 要开到 fork 的上游仓库，或报告/截图里有拿不准是否可以公开的内容（内部地址、业务数据、未公开的产品规划等）——即使已获授权，推送前也要向用户确认一次：说明推送到哪个仓库、仓库可见性、将公开的内容、已做的脱敏处理，列出拿不准的条目。用户确认后再推送，不确认就停在本地提交。私有仓库且没有上述内容时不必额外确认。

## 分支与提交

在临时 worktree 里完成，用户的工作树全程不切分支、不碰未提交改动：

```sh
git ls-remote --heads <推送 remote> audit/<日期><后缀>   # 再确认一次远端没有同名分支
git worktree add -b audit/<日期><后缀> <临时路径> <被审 commit>
```

- 分支名用第 1 步定下的后缀；万一此时又冲突，只给分支名换新后缀（目录和报告文件名不变），记入 progress.md。
- 把 `<AUDIT>/report.md` 复制到 worktree 中的报告路径：项目已有文档目录约定就放进去，否则 `docs/audit/<YYYY-MM-DD><后缀>-project-audit.md`。被报告引用的截图复制到同目录的 `<YYYY-MM-DD><后缀>-assets/` 并控制体积，报告里的引用路径同步改好；其余过程文件留在 `<AUDIT>`，不入库。
- 只提交报告及其引用的资源。提交信息遵循项目已有规范，没有规范时用 `docs(audit): 项目全面审查报告 <YYYY-MM-DD>`。
- 获授权时推送：`git -C <临时路径> push -u <推送 remote> <audit 分支>`。不推默认分支，不 force push。
- 全部完成后 `git worktree remove <临时路径>`；分支保留。

## PR/MR 内容

描述先写到 `<AUDIT>/pr-body.md`，再显式指定目标分支创建 **draft**（在临时 worktree 里执行）：

```sh
gh pr create --draft --base <目标分支> --title "<标题>" --body-file <AUDIT>/pr-body.md
glab mr create --draft --target-branch <目标分支> --title "<标题>" --description "$(cat <AUDIT>/pr-body.md)" --yes
```

fork 场景：GitHub 用 `--repo <上游仓库>` 并按需加 `--head <fork 所有者>:audit/<日期>`；GitLab 或拿不准参数时，不要试错，把命令交给用户执行。

标题：`项目审查：<YYYY-MM-DD> 全面审查报告与修复跟踪`（项目非中文时用对应语言）

描述结构：

```markdown
## 说明
本 PR/MR 承载 <日期> 项目审查的报告及后续修复。**报告中问题的修复提交到本 PR/MR**，修复约定见报告开头：
- 每个修复提交在 message 中引用问题编号，如 `fix(CD-03): …`
- 修完一条：勾选下方对应条目（如有），并把报告中该条状态改为"已修复"
- 判断有误或另排的条目在报告中更新状态并注明原因/去向
- S0/S1 全部处理后再转为 ready for review；合入前决定审查报告是否保留在仓库中

报告：<报告文件链接> ｜ 审查版本：<被审 commit>

## 概览
审查范围与手段一句话；问题数：S0 x / S1 x / S2 x / S3 x；需要决策 x 条

## 修复清单
### S0
- [ ] [CD-01] 标题 —— 位置（工作量 S）
### S1
- [ ] …
### S2
- [ ] …
### S3（观察项，不要求在本 PR 中处理）
- [UI-07] 标题

## 需要决策
- [PD-04] 标题：分歧要点（详见报告）
```

S0/S1 始终逐条列出。清单过长（超过约 60 条）时，S2/S3 只给数量和报告锚点，它们的进度以报告中的状态为准。

创建后把 PR/MR 链接写回报告元信息（在同一分支追加一个提交并推送），然后告诉用户。

## 无法提交时

未授权、用户未确认推送、有远端没有的提交而用户未同意推送、没有 remote、平台不受支持、CLI 未安装或未认证时：保留本地 `audit/<日期>` 分支和提交，把 `<AUDIT>/pr-body.md` 的路径告诉用户，说明缺什么、用户可以怎么提交（如登录 CLI 后执行的具体命令）。不改用其他托管方式，不绕过认证。
