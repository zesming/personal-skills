# 内部评审：达成一致

各维度的原始发现里一定有误报、重复、严重度失准和遗漏。这一步通过"独立质证"把它们筛干净，目的是让报告里每一条都经得起项目维护者的反驳。

## 第 1 步：汇总去重（主 agent）

- 合并各维度的发现到 `<AUDIT>/draft.md`（`<AUDIT>` 见 SKILL.md 开头）。
- 同一根因的多处表现合并成一条（如"产品上两个入口" + "UI 上两套样式" + "代码里两套实现"往往是一件事），保留各维度的证据。
- 校正严重度：风格问题标成 S0/S1 的降级，真风险标低了的升级。
- 证据明显不足的条目先退回原审查者补证据，补不出来就删除。
- 执行各维度提出的变异验证候选（见下文「变异验证」），结果写进对应条目的依据。
- 审查者提出的其他运行验证（集成链、端到端组合等）：挑会影响定级的几项。只跑现有测试的，在审查位置跑；要往仓库里加测试文件、或依赖项目 fixture / harness 的，在临时 worktree 里做，与变异验证共用同一个 worktree 和对照（单纯新写测试的验证不需要另跑对照），做完同样还原、删除。能在 verifier 约束内完成的（只读探针、单个现有测试文件），交给第 2 步的 verifier。结果写进条目依据，没做的写明"未验证"；耗时记进 progress.md。主 agent 也不做的话，重要条目会带着"未验证"进报告。
- 要判断某个失败是不是近期引入的（定级或修复方向取决于它）时，在临时 worktree 里做，不在审查位置或用户仓库切提交：先在失败的提交和一个已知通过的较早提交上各连跑几次，确认两端结果稳定（单次运行会被偶发失败带偏，不稳定的不往下定位；较早的提交也稳定失败，就不是近期引入的，到此为止），再在怀疑的提交和它的父提交上对照。对照定不下来才用 `git bisect run`：step 脚本和日志放在 `<临时路径>`、每个 bisect 一份，开始前在已知好、坏的提交上手动各跑一次确认退出码，脚本里先清 git 环境变量（见「保护用户仓库的 git 配置」）。
- 成立时可能到 S0/S1 的待查线索：交给对应维度的 verifier 作为可补报项（只给线索和位置），其余留在报告"待查线索"。
- 核对基线里每组失败用例都已有归宿（某个条目或"局限"，定性方法见 `references/tests.md` 方法 1）；缺的续用测试维度的审查者补，测试维度不在范围内时主 agent 自己定性或记入局限。
- 产品维度的"精简建议"拆成具体条目进入清单，和其他问题一样接受质证。
- 审查者写了"待问用户"的条目，问题和候选方案先记下来，供「向用户确认」使用。

## 第 2 步：全范围质证（第 1 轮）

派全新的 verifier（不是原审查者，不继承对话）。条目多时按维度拆成几个并行，共用部分同样写成一个文件（如 `<AUDIT>/verifier-common.md`）让各 brief 引用；它只写质证特有的要求，不放宽也不收紧 brief-common 的只读约束（包括审查者可以跑聚焦测试）。brief 只给：
- 待质证的条目（只给条目字段，不附原审查者的推理过程）
- `<AUDIT>/brief-common.md` 的路径：审查对象、问题格式、严重度、只读约束、不评判协作流程等都按它执行，其中"产出"一节不适用
- 对应维度 reference 的绝对路径（尤其是"常见误报，不要报"）；产品维度同时给 code.md 的绝对路径
- 分给它的验证项和待查线索（见第 1 步）
- 让它把质证结论写到 `<AUDIT>/verify-r<轮>-<维度或序号>.md`，只返回摘要；返回后主 agent 检查文件，写不了文件或宿主不允许 subagent 写结果文件时，按 SKILL.md 第 2 步让它在回复里返回全文、由主 agent 存档。它自报读过不该读的文件时：读到的内容涉及它所质证条目的判断的，那几条送复核轮；只读到流程状态的，在 consensus-log 记一笔

对每条，verifier 亲自打开引用的位置、尽量复现，给出结论之一并附依据：
- **确认**：问题成立，严重度和建议合理
- **修改**：问题成立，但严重度、范围、根因或修复建议需要调整（说明改成什么）。修复建议有多个方案却没给推荐项和取舍的，也按修改补上；要业务判断才能选的，写"待问用户"
- **驳回**：问题不成立（误读代码、已有处理、属于有意设计等），必须给出反证

**只有这一轮**允许补报遗漏，且只补报 S0/S1。

## 第 3 步：裁决（主 agent）

- 确认 → 已确认。
- 修改 → 合理就采纳并改为已确认；不合理的，连同理由进入复核。
- 驳回 → 先自己看反证；明确成立的标为已驳回，记入附录。拿不准的交给原审查者回应，要求给证据而不是重复观点。
- 补报的遗漏 → 作为新条目进入复核。
- 需要业务信息才能判断的取舍（某功能该不该删、某行为是否有意）→ 状态记为"待产品确认"，放进待问清单，不送复核轮；争议的关键是业务意图时也这样处理。
- 依据是"违反项目约定"的条目：先裁定判定该约定过时或矛盾的 CD 条目（见 `references/code.md`「agent 指令文件」）；它被确认后，依赖这条约定的条目重新判断，没有其他依据的驳回。

## 第 4 步：复核（第 2、3 轮）

只把尚未裁定的条目（有争议的驳回/修改、补报的遗漏）连同双方证据交给一个新的 verifier 裁定。复核轮**不再补报**新条目，只裁定指定条目。

## 停止条件

- 每条都处于终态（见 SKILL.md「状态」表），或只差用户判断，即停止质证，进入「向用户确认」。
- 同一条经过两轮来回、双方都拿不出新证据 → 存在分歧；靠用户的知识能判断的，放进待问清单。
- 第 3 轮结束仍未裁定的 → 未充分质证，报告里单独标注，交给用户。

同一类误报反复出现时，说明审查指南或范围理解有偏差，先修正理解再继续。

## 向用户确认（主 agent）

质证结束、写报告之前集中问一次，不要每轮裁决后都问。能当场定下的就当场定，"待产品确认"只留给用户确实判断不了的。提问偏好为"不打断"时跳过这一步，相关条目保留"待产品确认"。

- **先落档**：把问题写进 `<AUDIT>/questions.md`，每问记涉及编号、现状、候选方案及后果、推荐项、状态（已发未回 / 已答 / 视为无答复）和答复内容；progress.md 第 3 步记"已发问，已答 x/y"。会话中断后接续时，只重新列出"已发未回"的问题。
- **控制数量**：同一个决策涉及的多条合并成一问；业务问题不超过约 10 问（下面"一并问"的交付问题不计入），按严重度、以及一个回答能定几条来排序，超出的不问，保留"待产品确认"。
- **一并问**：授权或可见性仍是"待问"、报告是否入库拿不准、交付相关的约定被判定有问题、S0 要不要单独走 hotfix，都并进这同一条消息。
- **推送确认**：有任一公开风险（见 `references/pr.md`「敏感内容」「推送前确认」）、且授权已获或在这条消息里一起问时，在这里一并确认，免得到第 5 步才问、卡在最后一条消息。授权仍是"待问"的，把授权和推送确认合成一问（如"是否推送并开 draft PR/MR 到 <仓库>？按公开处理，将公开……"），答"是"两项都算确认。这一问放在消息最前面，写明将公开的内容：报告全文和 PR/MR 描述（安全条目只留占位；不入库时报告全文作为评论公开）；报告尚未写出，内容以列出的条目为准——列出将进报告的条目标题（含需要决策的）、将入库的截图和拿不准能否公开的条目，并说明之后新增拿不准的内容会再确认。推荐项是推送时，写明"回复'全部按推荐'即视为同意推送到 <仓库>（<可见性>）"。
- **可见性是事实问题**：不给推荐项，不在"全部按推荐"的范围内；用户没有明确回答的按公开处理。
- **问法**：每问给出选项和推荐项（可见性除外，见上），告诉用户可以回一句"全部按推荐"，也可以按编号只答一部分。环境里有结构化提问工具、且一次调用放得下全部问题时用它；放不下（这类工具常限制题数和选项数，如 Claude Code 每次最多 4 问、每问 2–4 个选项）或没有这类工具时，用一条普通消息列出全部问题。不要为塞进工具而合并不相关的问题，或把放不下的留成"待产品确认"——数量只按上一条"控制数量"控制。
- **处理答复**：
  - 选了一个方向 → 已确认，修复建议按所选方向写。
  - 说明是有意设计，或在"问题是否成立"的提问里选"保持现状" → 已驳回；安全漏洞或数据丢失、损坏类的 S0/S1 改为"接受风险"，留在正文。对"修复后保留 / 删除"这类提问，选"保留"不等于驳回缺陷。
  - 明确说判断不了、以后再说 → 保持原状态（待产品确认或存在分歧）。
  - 用户的下一条回复没提到的条目（如只说了"继续"）在 questions.md 里标"视为无答复"，保持原状态，不再追问；其中的授权问题按未授权处理、可见性按公开处理、推送确认按未确认处理，progress.md 记"已问未答"。
  - 用户提供了新事实（如"这个接口有外部调用方"）→ 主 agent 据此直接裁定，不再新开质证轮。
- **记录**：答复写进条目的"依据"（如"经用户确认（<日期>）：……"）和 questions.md，不再另记。答复里如有未公开的产品规划等内容，进报告前按 `references/pr.md`「敏感内容」处理。

## 变异验证（主 agent）

用于疑似假测试，或确认某个关键回归没有任何测试能发现；不用于证明现有测试有效，静态即可证明测试没有产品依赖（如没有引用任何产品代码）的也不需要变异。在系统临时目录下的临时 worktree（`git worktree add --detach <临时路径> <被审 commit>`，登记到 progress.md）里故意破坏被测实现（删掉关键逻辑、反转条件）。变异前先在这个 worktree 里不加变异跑一次全量作为对照（`<AUDIT>/baseline/` 是在审查位置跑的，环境可能不同）；要跑 E2E 时先停掉第 1 步启动的共享应用，或确认 E2E 连的是本 worktree 起的服务，否则测的是没被变异的代码；全部变异做完后重新启动共享应用，供后续质证复现 UI 条目。**一次只施加一个变异**，先跑候选测试（它相对对照新增失败就说明测试有效，不必再跑全量），再跑与对照相同的全量套件（必要时加上覆盖该代码的 E2E）：只有全量也没有新增失败，才能说"没有测试能发现这个回归"；只是候选测试通过，只能证明那个测试名不副实。每个变异跑完都用 `git -C <临时路径> checkout -- .` 还原、`git -C <临时路径> clean -fd` 清掉测试生成的未跟踪文件（不加 `-x`）（必须带 `-C <临时路径>`，在用户仓库里执行会清掉用户未提交的改动），再用 `git -C <临时路径> status --short` 确认干净后做下一个。判定以对照为准：相对对照没有新增失败，就是"没有测试能发现"。多个变异同时施加时出现的失败无法归因，不作为证据。全量套件较慢时只挑最关键的几个候选，并把耗时记进 progress.md。依赖需要联网安装才能跑时先问用户；做完 `git worktree remove --force <临时路径>`（被测文件已被改动，需要 `--force`；只对本流程自建的这个 worktree 这样做），并在问题依据里写明做法。

## 保护用户仓库的 git 配置（主 agent）

`git bisect run`、hook 等由 git 启动的进程会导出 `GIT_DIR` 等变量（在 worktree 里提交时，hook 拿到的也指向用户仓库），测试里的 `git init`、`git config` 继承后会改写用户仓库的 config；worktree 本身也和用户仓库共用同一个 config。
- 跑测试（含 bisect 的 step 脚本）的同一条命令或脚本里先 `unset $(git rev-parse --local-env-vars)`。
- 在审查位置第一次装依赖或跑测试之前（husky 等 prepare 脚本会改 `core.hooksPath`），把 `git -C <用户仓库> rev-parse --path-format=absolute --git-common-dir` 下的 config 复制到 `<临时路径>`。里面可能有带凭据的 remote 地址：只放临时目录，登记到 progress.md，收尾时删除。
- 之后每次自己跑完测试、每轮 subagent 返回后，以及第 5 步每次提交、推送之后，用 `diff` 对比一次（hook 也会改写它）；推送新增的 `[branch "<audit 分支>"]` 一节是预期的，确认只多了这一节后把备份更新为当前版本。
- 有变化就先停下其他运行，把改动告诉用户，只还原能确认是本流程写入的项（如 `core.bare`、测试用的 `[user]`、`core.hooksPath`），拿不准的问用户。

## 没有 subagent 时

主 agent 自己做质证，但要换一种方式看：逐条回到源码重新核对，刻意寻找反证（"如果这是有意设计，会有什么痕迹？"），再给结论。在报告里注明质证由同一 agent 完成。

## 编号

沿用审查时的编号，不重新编号（见 SKILL.md「问题格式」）。合并时被并入的编号写进主条目的状态，如"已确认（合并 UI-06）"；补报的新条目由主 agent 在裁决时统一接着该维度最大编号往后编（并行的 verifier 各自编号会撞号）。

## 记录

每轮的质证结论和裁决记到 `<AUDIT>/consensus-log.md`，用户答复见 questions.md。报告附录 A 按 `assets/report-template.md` 的要求汇总。
