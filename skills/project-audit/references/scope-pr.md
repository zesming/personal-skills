# 范围审查：审 PR/MR 的评论与结论

审 PR/MR 时读本文件：替换 SKILL.md 第 4、5 步；第 3 步提问用到「结论与确认」「发布前」；再审的范围计算在 `references/scope.md` 第 1 节。平台 CLI / API 的用法照 scope.md「平台 CLI / API」。

不写 report.md，不建分支，不开 PR/MR。要发的内容先写进 `<AUDIT>/review.md`：每条的编号、锚点（文件、行号、新旧版本哪一侧）、评论正文，再加上总评论和结论。它是发布的依据；发不出去时，它就是交给用户的本地报告。

**条目与标签**（按终态状态和严重度决定）：

| 状态 | S0/S1 | S2 | S3 |
|---|---|---|---|
| 已确认 | 必须改，计入结论 | 建议改，不阻断合入、不计入 | 总评论观察项 |
| 待确认（作者能答的意图类问题） | 待确认，使结论为 comment | 待确认，不计入 | 总评论观察项 |
| 待产品确认、存在分歧、未充分质证（集成方没答或"不打断"） | 写进总评论的"待确认"，使结论为 comment | 只留本地 | 只留本地 |
| 接受风险、已驳回 | 只留本地 | 只留本地 | 只留本地 |

- "待确认"的正文写成给作者的问题。安全类条目、范围外线索另按「发布前」。

**锚点**：
- 行内评论只能挂在平台 diff 里可评论的行上（通常是 diff hunk 内的新增行和上下文行；被删除的行挂在旧版一侧）。按 `git diff -U3 <base> <head>` 算出可评论的行，发前逐条校验；平台的 diff 可能因大文件截断、改名识别而不同，被拒时见「发布」。
- 评论尽量绑定被审版本（平台支持时）。平台不支持其他侧、多行等写法时，拿不准就写进总评论。
- 问题在 diff 外（hunk 外、未改动的文件）：挂到触发它的那一行改动上（引入调用的那行、改了签名的那行），正文写明实际位置。找不到这样的行，或问题不对应具体代码（意图不符、整体缺测试、夹带），写进总评论。
- 实际位置写 `路径:行号`；能生成平台链接时，用 head sha 的固定链接。
- 同一根因的多处只发一条，挂在最主要的位置，其余位置列在正文里。

**评论格式**：语言跟随 PR/MR 描述，没有描述时跟随项目；对事不对人；不出现本机路径和审查流程的内部用语。UI 条目的截图不能引用本地路径：改写成文字说明并注明截图在审查者本地；平台支持上传且用户确认后，才上传。

    **S1 · 必须改** · 本次引入｜<标题>
    <现象与依据，一到三句；diff 外的位置写路径:行号或链接>
    建议：<改成什么样；有多个方案时给推荐项>
    <!-- project-audit id=CD-03 run=<AUDIT 目录名> -->

- 末行标记供重复运行时识别，原样保留。`run` 是本次工作目录名，编号跨次运行会重复，去重和再审靠位置与根因加 run 区分。
- 平台会把 HTML 注释渲染出来时（发第一条后检查返回或页面），改用平台上不显眼的等价写法，或只在 review.md 本地记录映射；去重以本地记录加位置、根因为准。

**总评论**（与结论一起提交），依次写：
- 结论和一句理由（首行；跟随评论语言，如"结论：需修改"）；旧结论的写法见「结论与确认」；
- 必须改 / 建议改 / 待确认的条数；
- 没有锚点的问题（同样格式）；
- 审查版本 `<base 短 sha>..<head 短 sha>` 和审查手段，未覆盖的部分；
- 观察项（S3，不发行内评论）：列在末尾"观察项（不要求处理）"下，一行一条；
- 末行 `<!-- project-audit summary base=<base sha> head=<head sha> run=<AUDIT 目录名> -->`。标记放在随结论提交的那一条里（总评论拆分时放在带结论的首条；之后单独补交结论时，补交的那条带标记）。

内容超过平台评论长度上限时，其余部分拆成后续普通评论。

**结论与确认**：
- 判定：
  - 有已确认、未修复的 S0/S1（接受风险的除外）→ request changes；
  - 没有这类条目，但有待确认的 S0/S1 → comment，总评论写明在等什么答复；
  - 都没有 → approve。
  - 仓库配置了 CI，但在被审 head 上未完成（没跑或仍在跑）或失败且未定性，且本机没有跑过对应检查时，拟定结论最多是 comment，总评论写明。没有 CI 时以本机基线为准；仅静态审查又没有 CI 结果时，最多 comment。
- 确认：approve 是用户本人签字，request changes 也代表用户。第 3 步集中提问时给出拟定结论和理由，用户确认后才提交；拟定 approve 时问法写明"回复'全部按推荐'即视为提交 approve"；公开仓库另有未计入结论的存量安全问题时，问法里写明条数和严重度，细节见 security.md。之后条目状态变化使结论改变时，发布前再确认一次。
- 按 comment 提交、拟定结论写进总评论首行的情况：
  - 结论未确认（"不打断"、已问未答）：评论照发（公开仓库另需发前确认），以 comment 提交；用户之后确认时，再单独提交结论（先过「发布前」的 head 与状态检查）；
  - 平台没有 request changes：不 approve，首行写需修改；
  - 审的是当前账号自己的 PR/MR（平台上的作者与登录用户相同）：不问拟定结论；
  - 提交结论被平台拒绝；
  - PR/MR 已合入或已关闭，或 head 已变（见「发布前」）。
- 本账号在这个 PR/MR 上已有结论、与本次实际提交的不一致时（含本次以 comment 提交）。撤销是以用户身份的写操作，需要发评论的授权；未获授权或整体不发时不撤，在收尾总结里单列，提示用户自行处理。旧 approve 在提交本次 review 前撤；旧 request changes 在本次结论提交成功后才撤。按下面处理：
  - 旧 approve：撤销，不需要确认结论；平台撤不掉时，总评论首行写明"此前的 approve 不代表当前结论"，并在收尾总结里单列，提示用户用有权限的方式撤销。
  - 旧 request changes：只在用户确认的结论不是 request changes、且 head 仍是被审 head 时撤销（问法里写明"确认后会撤销此前的 request changes"）；其余情况（结论未确认、head 已变、平台拒绝等降为 comment）一律保留，总评论首行写明"此前的 request changes 仍有效，当前拟定结论为 …"，并在收尾总结里单列；该撤而平台撤不掉时，补一条普通评论说明，同样单列。
- approve 尽量绑定被审 head（平台支持时）；不支持的，提交前紧挨着再查一次 head。

**发布前**：
- 再查 head 和状态：PR/MR 已合入或已关闭，一律不提交 approve / request changes。head 已不是被审的 head 时告诉用户，让用户选择：按已审版本发评论（评论绑定被审版本，总评论注明版本，结论最多是 comment），或先补审新提交。平台不能把评论绑定到版本的，只能先补审，或全部条目写进总评论。"不打断"时默认不发，把 review.md 交给用户。
- 选择补审时，在同一个工作目录里以 range.md 的旧 head 为起点算增量；增量只送审查和质证；review.md 的锚点按新的净 diff 重新校验；本轮条目在新 head 上逐条核对（方式同「再审」，但不回复），已修复的移出；旧 head 不是新 head 的祖先时，按 scope.md 整体重审；结论改变时重新确认。
- 授权照 `references/pr.md`「前置检查」，其中"推送"读作"发评论"。
- 非公开仓库：评论直接发，不做发前确认。安全类问题（含存量）也写在 PR/MR 里让作者修，但不写具体利用方式和密钥值（只写位置和类型）。
- 公开仓库：
  - 发前确认一次（照 `references/pr.md`「敏感内容」「推送前确认」，"推送"读作"发评论"；通常已在第 3 步集中提问时做过），列出将发的条目标题和结论。没确认（没答或"不打断"）的，不发，停在本地，把 `<AUDIT>/review.md` 交给用户。
  - 本次引入的安全类问题：不发行内评论，不写位置和利用方式；总评论只写"有 n 条安全相关问题，将另行沟通"，照常计入结论；细节写进 `<AUDIT>/security.md`，告诉用户，由用户私下转给作者或走安全渠道。审的是自己的 PR/MR 时，平台上不提及，直接交给用户。
  - 存量的安全类问题已经在线上：PR/MR 上不提及、不计数、不影响结论，细节写进 security.md，单独交给用户。
- 范围外的待查线索不发到 PR/MR，只告诉用户。

**去重**：发前读平台上已有的全部评论（行内评论、普通评论、review 正文）。
- 当前账号发过、带本 skill 标记的：同一位置、同一根因的不再发；状态有变化的按「再审」处理。
- 别人（含其他评审者）已提过的同一问题不单独发，在总评论里写"同意 <链接> 的意见"。
- 判断是不是同一条，看位置和根因，不看措辞。

**发布**：
- 平台能一次提交整份 review（行内评论、总评论、结论）的，一次提交，避免中途失败留下半套；提交体里每条行内评论带正文、路径、行号、所在侧、被审版本，多行评论带起止行和起止侧。仓库用 PR/MR 所在（目标）仓库，不是 head 仓库。
  - 有一条行号不在 diff 里会导致整份被拒：把出错的条目移进总评论再重发。
  - 报错或超时后重发之前，先查平台上已有的 review，按 summary 标记和 head 看是否已发出，避免重复提交整份。
  - 用户已有未提交的草稿 review 导致失败时，告诉用户，不替用户删除。
- 只能逐条发的平台：每条行内评论发完检查返回里确实挂在了行上（没挂上说明变成了普通评论）；没挂上就查明原因（行不在 diff 里、版本引用过期），修正后重发，仍不行移进总评论。总评论和结论另发。
- 平台缺某项能力时：缺行内评论，全部写进总评论（带路径:行号）；缺 approve，结论写在总评论首行。
- 逐条发的，每发成功一条就把返回的 ID 记进 review.md。命令报错或超时时，先按标记查平台上已经发出的，只补发剩下的，不整批重发。
- 发完把链接记进 progress.md。

**发不出去时**（未授权、head 已变而用户未选择、公开仓库未确认、平台不支持、没有可用且已认证的 CLI 或 API）：把 `<AUDIT>/review.md` 的路径交给用户，说明缺什么、用户可以怎么提交（如登录 CLI 后执行的具体命令），不绕过认证。`references/pr.md`「无法提交时」里关于 audit 分支和 pr-body.md 的部分不适用。

**再审**（范围计算见 scope.md）：上次发的条目在新 head 上逐条核对：
- 已修复 → 在原讨论下回复"已在 <短 sha> 修复"（先看是否已回复过）；本账号发起的讨论标为已解决（平台支持时）。写在总评论里、没有讨论线程的条目，在新总评论里更新状态；
- 仍存在 → 不重发，照常计入结论；
- 作者回复了反对意见 → 作为证据送质证。被驳回的，回复确认并标为已解决；问题成立的，回复一次证据；仍有分歧的留给用户和其他评审者决定，不反复争论。

结论按所有仍未解决的条目重新判定，按「结论与确认」提交（含撤销旧结论）。
