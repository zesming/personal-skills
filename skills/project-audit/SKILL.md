# project-audit

被委派执行子任务的 subagent 不使用本 skill，直接完成 brief 里的任务。

本 skill 同时用于 Claude Code 和 Codex。文中的 reviewer / verifier 指角色，不是 agent 名字：从当前环境里选最匹配的 subagent，没有就用通用 subagent，并把角色要求写进 brief。续用已有 subagent：Claude Code 用 SendMessage，Codex 用 followup_task；不支持续用时重新派一个，把需要的上下文写进 brief。派审查类 subagent 时不让它继承当前对话（Codex 中用 `fork_turns="none"`）。文中的 `references/…`、`assets/…` 都相对本 skill 根目录；`<AUDIT>` 指第 1 步在用户原仓库根目录建的工作目录 `.audit/<日期><后缀>/` 的绝对路径，传给 subagent 时一律展开成绝对路径。`<临时路径>` 指系统临时目录下新建的目录，不放在仓库里。

## 这个 skill 产出什么

一份经过质证的问题清单，不是修复。审查阶段不改项目代码；产物只有：工作目录里的过程记录、入库的审查报告、一个 draft PR/MR。后续修复提交到这个 PR/MR 的分支上。

## 原则

- **证据优先**：每条问题都要有可核对的依据——`文件:行号`、可复现的操作路径、截图、命令输出、提交记录。拿不出依据的不算问题。
- **先理解意图，再判断冗余**：说一个功能多余、一段设计不合理之前，先读 README、文档、提交历史和相关 issue，弄清它为什么存在。没有使用数据时，"冗余"只是假设，要标明置信度和验证方式。
- **偏向做减法**：修复建议优先考虑删除、合并、简化，其次才是新增。每条建议说清改完的样子，而不是"建议优化"。
- **抓大放小**：报告的价值在于让人知道先修什么。同一根因的多处表现合并成一条；风格偏好、无实际影响的写法不进清单。宁可 20 条都站得住，不要 80 条里混着一半噪音。
- **诚实标注覆盖范围**：写清审了什么、没审什么、用了什么手段（静态阅读 / 运行测试 / 实际操作应用），不把抽样结论说成全量结论。
- **不扩散敏感信息**：密钥、凭据、个人数据只写位置和类型，不写值；未修复的安全类问题细节不发到公开位置，截图入库前检查有无个人数据或 token（见 `references/pr.md`）。

## 流程

### 1. 摸底与定范围

**接续**：先看仓库根目录下有没有未完成的 `.audit/*/progress.md`，有就问用户是否从记录的步骤接着做。

**确认范围与授权**：
- 用户只要求某些维度或某个模块（"审一下测试""看看支付模块的技术债"）时，只审指定部分，其余流程不变。
- 本地 audit 分支和提交总会做；需要授权的是**推送分支和开 draft PR/MR**。用户显式调用本 skill（`/project-audit`、`$project-audit`）或在请求中明确要求开 PR/MR、推送审查结果，视为已授权，除非用户另有说明（如"别开 PR"）；否则记为"待问"。
- 用户没有明确要求审查或出报告、只是由宽泛说法触发时（"看看项目有什么问题"；"全面审查/审计这个项目"这类已明确要审查的不算），全量审查代价不小：只做只读摸底（读文档、看结构），用一条消息说明打算审的范围和维度，并一并问是否推送开 PR/MR，**等用户确认后**再建工作目录、worktree、跑基线和派 subagent。用户不继续就到此为止，不留下任何改动。

**确认环境与被审版本**（报告行号、PR 基线都以此为准，在这里一次定死）：
- 不是 git 仓库：照常审查并写报告，跳过第 5 步，报告留在工作目录交给用户，报告里删去"修复约定"一节。
- 记录 remote（判断 GitHub / GitLab / 其他）。有多个 remote 或仓库是 fork 时问用户推到哪里（`<推送 remote>`）、PR/MR 开到哪个仓库（`<目标 remote>`）；只有一个 remote 时两者相同。下面的远端比较以 `<目标 remote>` 为准。没有 remote 时跳过远端相关检查，第 5 步只做本地提交。查仓库可见性（GitHub `gh repo view --json visibility,isFork`，GitLab `glab repo view`），不是 private 或查不出来都按公开处理。
- 基线分支：当前在默认分支上就用它；在其他分支上时问用户审哪个分支。
- 被审 commit = `git rev-parse <基线分支>`（不用 `HEAD`）。先用 `git ls-remote --exit-code --heads <目标 remote> <基线分支>` 确认远端分支存在（本地跟踪引用可能已过期，不能代替），再 `git fetch --prune <目标 remote>` 后对比：
  - 本地领先（`git rev-list --count <目标 remote>/<基线分支>..<被审 commit>` > 0）：告诉用户，让用户选择改审远端版本，还是同意这些提交随 audit 分支一起推送。
  - 本地落后（反向计数 > 0）：告诉用户，问是否改审远端最新版本。
  - 基线分支在远端不存在：同样视为"含远端没有的提交"，让用户选择换一个远端已有的分支作为审查和 PR/MR 目标，或只做本地提交、不推送。
  - 用户换了分支或改审远端版本时，对新的被审 commit 重新做上述对比。
  - 用户选择之前不推送任何东西；选择结果和 PR/MR 目标分支记入 progress.md。
- 审查位置：被审 commit 就是当前 `HEAD` 且工作区干净时，直接在仓库里审；否则用 `git worktree add --detach <临时路径> <被审 commit>` 在干净副本里审（不碰用户未提交的改动；依赖需要重新安装时先问用户）。
- 以上信息记入 progress.md。

在**用户原仓库根目录**建工作目录 `<AUDIT>`。后缀在这里一次定下：`.audit/<YYYY-MM-DD>/` 目录、本地分支 `audit/<YYYY-MM-DD>`、远端同名分支（`git ls-remote --heads`）任一已存在（且不是要接续的），就统一加 `-2` 等后缀，目录、分支、报告文件名共用，记入 progress.md。之后所有引用都用它的绝对路径——它不能放进任何临时 worktree，否则删 worktree 时会被一起删掉。`git rev-parse --git-path info/exclude` 指向的文件还没忽略 `.audit/` 时追加这一条，不改项目的 `.gitignore`。按 `assets/progress.md` 建 `progress.md`，每完成一步更新。

**建立项目画像**，写入 `<AUDIT>/profile.md`：
- 产品定位与目标用户、产品要解决的核心问题（来自 README、文档、首页文案、代码中的命名）
- 功能清单：从路由、菜单、命令、API 端点、配置开关、文档里归纳
- 核心用户路径 3–7 条（如"首次使用 → 完成第一个核心任务"）
- 技术栈、模块地图、入口、构建与运行方式
- 测试体系：框架、目录、CI 配置、是否有覆盖率配置
- 热点：`git log --since=6.months --format= --name-only | sort | uniq -c | sort -rn | head -30` 找改动最频繁的文件

**定维度**：四个维度默认都审，按项目形态调整：
- 没有图形界面（库、CLI、后端服务）：UI 维度改为"接口 / CLI / 配置的易用性"，并入产品维度一起审。
- 几乎没有测试：测试维度聚焦"哪些高风险路径最该先补测试"，不逐条列"未覆盖"。

**定范围**：代码量大（粗略超过 5 万行）或是 monorepo 时，按"核心用户路径涉及的模块 + 改动热点 + 复杂度最高的模块"选范围，其余列为未覆盖。monorepo 里看不出用户关心哪个子项目时先问。

**跑基线**（主 agent 在审查位置统一做，避免多个 subagent 抢端口和构建目录）：
- 先读测试配置和脚本。需要真实凭据、连接非本地数据库或外部服务的套件，先问用户再跑。
- 跑测试套件、项目已配置的覆盖率、项目已有的 lint / 复杂度工具；输出存到 `<AUDIT>/baseline/`，覆盖率等报告尽量直接指定输出到那里。跑前跑后各看一次 `git status`，测试在仓库里留下的产物要清理掉。
- 只用项目自带或本机已装的工具；需要联网安装依赖时先问用户。跑不起来就如实记录原因。
- 需要审 UI 且能运行时，由主 agent 启动一次本地应用，把地址交给产品和 UI 维度共用。

用几行话告诉用户：画像要点、审查范围与维度、会不会实际运行应用。授权仍是"待问"时在这里问一句，但不必等回答，继续往下审。

### 2. 分维度审查

每个维度派一个 reviewer 并行审查。brief 自包含，包括：
- 被审 commit、审查位置（代码所在的绝对路径，只读这里的代码）、项目画像和基线输出的绝对路径、审查范围、本地应用地址（如有）
- 该维度的审查指南：`references/product.md`、`references/ui.md`、`references/code.md`、`references/tests.md` 的绝对路径，让它自己读
- 下面的「问题格式」「严重度」，以及「原则」中的证据与敏感信息要求
- "只读：不修改项目文件，不执行会改动仓库或外部状态的命令；可以运行只读命令、操作已启动的本地应用，截图等证据只写入 `<AUDIT>/evidence/`；不要启用 project-audit skill"
- 要求以文本返回问题清单，并列出它创建的临时文件和启动的进程

不给它别的维度的发现，让每个维度独立判断。主 agent 把返回内容存为 `<AUDIT>/findings-<维度>.md`。

需要改动代码才能做的验证（如测试维度的变异验证）由 reviewer 提出候选，主 agent 在第 3 步汇总时执行，结果写进对应条目的依据，见 `references/tests.md`。

环境里没有 subagent 时，主 agent 按维度依次自己审，一个维度审完再进入下一个。

### 3. 内部评审，达成一致

按 `references/consensus.md` 执行：汇总去重 → 全范围质证 → 裁决 → 只对有分歧的条目复核，直到每条问题都有终态，最多 3 轮。

这一步决定报告的可信度，不要因为条目多就跳过。

### 4. 产出报告

按 `assets/report-template.md` 把报告写到 `<AUDIT>/report.md`（第 5 步再放进临时 worktree，不要写进用户的工作树）。报告语言跟随项目（项目文档是中文或无明确语言时用中文）。仓库按公开处理时，安全类条目在这里就按 `references/pr.md`「敏感内容」写成占位，细节写进 `<AUDIT>/security.md`。报告开头的"修复约定"一节必须保留（非 git 项目除外）：后续修复可能在没有加载本 skill 的会话里进行，约定要随报告走。

### 5. 提交 PR/MR

按 `references/pr.md` 执行：在一个新的临时 worktree 里从被审 commit 建 `audit/<日期>` 分支并提交报告（用户的工作树始终不切分支），获授权时推送并开以第 1 步确定的目标分支为目标的 **draft** PR/MR，描述里放可勾选的问题清单，写明"后续修复都在此 PR/MR 中完成"。到这一步授权仍是"待问"就再问一次，没有回答按未授权处理；有敏感信息公开风险时，即使已授权也先向用户确认（见 `references/pr.md`「敏感内容」）。未授权、没有 remote 或没有可用 CLI 时，停在本地提交，并把 PR 描述交给用户。不推默认分支，不 force push，不合入。

### 6. 收尾

- 删除本流程建的临时 worktree（`git worktree remove`），停掉本流程启动的本地服务和模拟器，删掉登记的临时文件。
- `<AUDIT>` 保留（已被 git 忽略），里面的过程记录后续修复时可参照；报告本身以 audit 分支里的版本为准。
- 给用户的总结只说：问题总数和严重度分布、最该先修的 3–5 条、需要用户决定的点、报告和 PR/MR 链接、`<AUDIT>` 位置（并提一句已在 `.git/info/exclude` 里忽略 `.audit/`）。不把整份报告贴进对话。

## 问题格式

每条问题一段，字段齐全：

```
### [CD-03] 订单状态在三处各自维护，存在不一致窗口
- 维度：代码 | 严重度：S1 | 工作量：M | 置信度：高 | 状态：已确认
- 位置：src/order/service.ts:120-188，src/order/store.ts:45，src/api/order.ts:77
- 现象：……（客观描述，不带结论）
- 依据：……（为什么这是问题：引用代码、复现步骤、命令输出、违反的原则或项目自身约定）
- 影响：……（对用户 / 维护 / 风险的具体后果）
- 修复建议：……（改成什么样；有多个方案时给推荐项和取舍）
```

编号前缀：PD 产品、UI 界面与交互、CD 代码、TS 测试。各维度先自行编号，第 3 步结束后统一重新编号并冻结，此后不再变动。合并后跨维度的问题用主维度前缀，在"维度"里列出全部相关维度。工作量：S（半天以内）、M（一到两天）、L（更多，建议拆成子项）。

## 严重度

- **S0 阻断**：核心路径走不通、数据丢失或损坏、安全漏洞、测试造假掩盖了真实失败。应立即修；经用户同意可以单独走 hotfix PR，在清单里注明去向。
- **S1 重要**：明显伤害用户体验或可维护性、已知会出错的潜在风险、重要路径没有测试保护、明显违背产品目标的设计。本 PR/MR 内修。
- **S2 一般**：改了更好，影响有限或局部。可在本 PR/MR 中顺手修，也可另排，另排时注明去向。
- **S3 观察**：值得留意的趋势或假设，暂不需要行动，或需要更多信息（如使用数据）才能判断。

## 状态

| 状态 | 含义 | 进报告正文 |
|---|---|---|
| 已确认 | 质证通过 | 是 |
| 存在分歧 | 两轮来回仍无新证据，交用户判断 | 是，列入"需要决策" |
| 待产品确认 | 需要业务信息才能判断的取舍 | 是，列入"需要决策" |
| 未充分质证 | 达到轮数上限时仍未裁定 | 是，列入"需要决策"并单独标注 |
| 已驳回 | 被反证推翻 | 否，只进附录 |
| 已修复 / 误判 / 另排 | 后续修复阶段更新 | 原地更新状态并注明提交或原因 |

拿不出依据、只是怀疑的点不作为问题条目，可以写进报告"审查范围与局限"作为待查线索。

## 后续修复

用户之后要求按报告修复时：在 audit 分支上修（已合入或关闭则问用户）；用户工作区有未提交改动时不要直接切分支，先问用户，或用 `git worktree add <持久路径> <audit 分支>` 在单独的工作树里修（修复可能持续多天，不要放在系统临时目录；默认放在仓库同级的 `<仓库名>-audit-fix/`，或问用户）。按报告开头的"修复约定"执行。基线分支有更新时用 merge 同步，不 rebase、不 force push。用 devflow 之类的开发流程做修复时，其中"切分支、开 PR、合入、删分支"的步骤以本 PR/MR 为准，其余照常。
