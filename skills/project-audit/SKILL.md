# project-audit

被委派执行子任务的 subagent 不使用本 skill，直接完成 brief 里的任务。

本 skill 同时用于 Claude Code 和 Codex。文中的 reviewer / verifier 指角色，不是 agent 名字：从当前环境里选最匹配的 subagent，没有就用通用 subagent，并把角色要求写进 brief。审查和质证 subagent 要能把结果写进 `<AUDIT>`：被定义为完全只读、不能写文件的 agent 不选，改用通用 subagent，把只读约束写进 brief。续用已有 subagent：Claude Code 用 SendMessage，Codex 用 followup_task；不支持续用时重新派一个，把需要的上下文写进 brief。派审查类 subagent 时不让它继承当前对话（Codex 中用 `fork_turns="none"`）。任何 subagent 因用量上限、超时等中断时，续用同一个让它从中断处继续，不要重新派一个从头来过（用量上限通常要等额度恢复，立即重试多半还会失败，拿不准就问用户）；为此派出后把 subagent ID 记入 progress.md。只能改派新 subagent 时，让它接着已有的结果文件往下写，不要覆盖。文中的 `references/…`、`assets/…` 都相对本 skill 根目录；`<AUDIT>` 指第 1 步在用户原仓库根目录建的工作目录 `.audit/<日期><后缀>/` 的绝对路径，传给 subagent 时一律展开成绝对路径。`<临时路径>` 指系统临时目录下新建的目录，不放在仓库里。

## 这个 skill 产出什么

一份经过质证的问题清单，不是修复。审查阶段不改项目代码；产物只有：工作目录里的过程记录、审查报告（按项目约定入库，或只放在 PR/MR 里）、一个 draft PR/MR。后续修复提交到这个 PR/MR 的分支上。

## 原则

- **证据优先**：每条问题都要有可核对的依据——`文件:行号`、可复现的操作路径、截图、命令输出、提交记录。拿不出依据的不算问题。
- **先理解意图，再判断冗余**：说一个功能多余、一段设计不合理之前，先读 README、文档、提交历史和相关 issue，弄清它为什么存在。没有使用数据时，"冗余"只是假设，要标明置信度和验证方式。
- **偏向做减法**：修复建议优先考虑删除、合并、简化，其次才是新增。每条建议说清改完的样子，而不是"建议优化"。
- **抓大放小**：报告的价值在于让人知道先修什么。同一根因的多处表现合并成一条；风格偏好、无实际影响的写法不进清单。宁可 20 条都站得住，不要 80 条里混着一半噪音。
- **诚实标注覆盖范围**：写清审了什么、没审什么、用了什么手段（静态阅读 / 运行测试 / 实际操作应用），不把抽样结论说成全量结论。
- **不扩散敏感信息**：密钥、凭据、个人数据只写位置和类型，不写值；未修复的安全类问题细节不发到公开位置，截图入库前检查有无个人数据或 token（见 `references/pr.md`）。

## 流程

### 1. 摸底与定范围

**接续**：先看仓库根目录下有没有未完成的 `.audit/*/progress.md`，有就问用户是否从记录的步骤接着做；`questions.md` 里有状态为"已发未回"的问题（见 `references/consensus.md`「向用户确认」）时，在同一条消息里重新列出它们，其他的不再问。

**确认范围与授权**：
- 用户只要求某些维度或某个模块（"审一下测试""看看支付模块的技术债"）时，只审指定部分，其余流程不变。
- 本地 audit 分支和提交总会做；需要授权的是**推送分支和开 draft PR/MR**。用户显式调用本 skill（`/project-audit`、`$project-audit`）或在请求中明确要求开 PR/MR、推送审查结果，视为已授权，除非用户另有说明（如"别开 PR"）；否则记为"待问"。
- 用户没有明确要求审查或出报告、只是由宽泛说法触发时（"看看项目有什么问题"；"全面审查/审计这个项目"这类已明确要审查的不算），全量审查代价不小：只做只读摸底（读文档、看结构），用一条消息说明打算审的范围和维度，并一并问是否推送开 PR/MR，**等用户确认后**再建工作目录、worktree、跑基线和派 subagent。用户不继续就到此为止，不留下任何改动。

**确认环境与被审版本**（报告行号、PR 基线都以此为准，在这里一次定死）：
- 不是 git 仓库：照常审查并写报告，跳过第 5 步，报告留在工作目录交给用户，报告里删去"修复约定"一节。
- 记录 remote（判断 GitHub / GitLab / 其他）。有多个 remote 或仓库是 fork 时问用户推到哪里（`<推送 remote>`）、PR/MR 开到哪个仓库（`<目标 remote>`）；只有一个 remote 时两者相同。下面的远端比较以 `<目标 remote>` 为准。没有 remote 时跳过远端相关检查，第 5 步只做本地提交。查仓库可见性（GitHub `gh repo view --json visibility,isFork`，GitLab `glab repo view`），不是 private 或查不出来都按公开处理。
- 基线分支：当前在默认分支上就用它；在其他分支上时问用户审哪个分支。
- 被审 commit = `git rev-parse <基线分支>`（不用 `HEAD`）。先用 `git ls-remote --exit-code --heads <目标 remote> <基线分支>` 确认远端分支存在（本地跟踪引用可能已过期，不能代替），再 `git fetch --prune <目标 remote>` 后对比：
  - 本地领先（`git rev-list --count <目标 remote>/<基线分支>..<被审 commit>` > 0）：告诉用户，让用户选择改审远端版本，还是同意这些提交随 audit 分支一起推送。
  - 本地落后（反向计数 > 0）：告诉用户，问是否改审远端最新版本。
  - 基线分支在远端不存在：同样视为"含远端没有的提交"，让用户选择换一个远端已有的分支作为审查和 PR/MR 目标，或只做本地提交、不推送。
  - 用户换了分支或改审远端版本时，对新的被审 commit 重新做上述对比。
  - 用户选择之前不推送任何东西；选择结果和 PR/MR 目标分支记入 progress.md。
- 审查位置：被审 commit 就是当前 `HEAD` 且工作区干净时，直接在仓库里审；否则用 `git worktree add --detach <临时路径> <被审 commit>` 在干净副本里审（不碰用户未提交的改动；依赖需要重新安装时先问用户）。
- 以上信息记入 progress.md。

**读项目约定**：AGENTS.md、CLAUDE.md、CONTRIBUTING、提交与分支命名规范等。其中关于代码、产品和测试的约定是审查标准（"违反项目自身约定"是有力的依据）；提交、分支、PR 规范只用于交付——决定报告是否入库（见 `references/pr.md`「报告放在哪里」）、audit 分支名（项目规定了分支前缀时，在 `audit/<日期>` 前按约定加前缀）和提交信息，不作为审查依据。这些文件本身也在代码维度接受审查（见 `references/code.md`「agent 指令文件」），经质证确认过时或矛盾的约定不再作为判定依据。结论在下面建好 progress.md 后记入，并写进画像。

在**用户原仓库根目录**建工作目录 `<AUDIT>`。后缀在这里一次定下：`.audit/<YYYY-MM-DD>/` 目录、本地分支 `<前缀>audit/<YYYY-MM-DD>`（无前缀约定时为空）、远端同名分支（`git ls-remote --heads`）任一已存在（且不是要接续的），就统一加 `-2` 等后缀，目录、分支、报告文件名共用。最终分支名记为 `<audit 分支>`，写入 progress.md，后文都用它。之后所有引用都用 `<AUDIT>` 的绝对路径——它不能放进任何临时 worktree，否则删 worktree 时会被一起删掉。`git rev-parse --git-path info/exclude` 指向的文件还没忽略 `.audit/` 时追加这一条，不改项目的 `.gitignore`。按 `assets/progress.md` 建 `progress.md`，每完成一步更新。

**建立项目画像**，写入 `<AUDIT>/profile.md`：
- 产品定位与目标用户、产品要解决的核心问题（来自 README、文档、首页文案、代码中的命名）
- 功能清单：从路由、菜单、命令、API 端点、配置开关、文档里归纳
- 核心用户路径 3–7 条（如"首次使用 → 完成第一个核心任务"）
- 技术栈、模块地图、入口、构建与运行方式
- 测试体系：框架、目录、CI 配置、是否有覆盖率配置
- 项目约定：影响审查标准和报告交付的条目
- 热点：`git log --since=6.months --format= --name-only | sort | uniq -c | sort -rn | head -30` 找改动最频繁的文件

**定维度**：四个维度默认都审，按项目形态调整：
- 没有图形界面（库、CLI、后端服务）：UI 维度改为"接口 / CLI / 配置的易用性"，并入产品维度一起审。
- 几乎没有测试：测试维度聚焦"哪些高风险路径最该先补测试"，不逐条列"未覆盖"。

**定范围**：代码量大（粗略超过 5 万行）或是 monorepo 时，按"核心用户路径涉及的模块 + 改动热点 + 复杂度最高的模块"选范围，其余列为未覆盖。monorepo 里看不出用户关心哪个子项目时先问。

**估算成本**：每个审查维度派一个 subagent，质证再按条目量派一到数个，另有最多两轮复核；在中等规模项目上每个通常要十几分钟、数十万 token。据此粗估总量，放进本步结尾给用户的摘要。达到上面"定范围"的门槛（大项目或 monorepo）时，在跑基线**之前**把范围和预估告诉用户，等用户选择全量、缩小范围、按维度分批派发（分批只是派发顺序，所有维度审完才进入第 3 步），或省用量（见下）。

**模型与推理档位**：环境允许按 subagent 指定模型或推理档位时，审查和质证用不低于主 agent 当前的配置。用户要求省用量（在请求里或任何时候）时，先建议缩小范围或分批；确实要降档，只降第 2 步的审查 subagent，质证不降——它决定报告的可信度。降档情况记入 progress.md 和报告的"审查手段"。不写死具体模型名；环境不支持按 subagent 指定时不处理。预定义的 subagent 可能固定了较低的模型，拿不准时选能继承主 agent 配置的通用 subagent。

**提问偏好**：用户或调用方明确说过"跑完再看""别打断"、或声明是非交互运行时，记为"不打断"：第 3 步不集中提问，需要用户判断的条目直接保留"待产品确认"；流程里其他需要问用户的点，取不产生外部副作用的选项（如不推送、不开 PR/MR）；各选项都没有外部副作用时（如审哪个分支或子项目、报告是否入库），取推荐项或更保守的一项。这些取舍记入 progress.md 和报告的"局限"。不要靠猜测判断环境是否可交互；没有说明时记为"可提问"。

**跑基线**（主 agent 在审查位置统一做，避免多个 subagent 抢端口和构建目录）：
- 先读测试配置和脚本。需要真实凭据、连接非本地数据库或外部服务的套件，先问用户再跑。
- 跑测试套件、项目已配置的覆盖率、项目已有的 lint / 复杂度工具；输出存到 `<AUDIT>/baseline/`，覆盖率等报告尽量直接指定输出到那里。跑前跑后各看一次 `git status`，测试在仓库里留下的产物要清理掉。
- 只用项目自带或本机已装的工具；需要联网安装依赖时先问用户。跑不起来就如实记录原因。
- 需要审 UI 且能运行时，由主 agent 启动一次本地应用，把地址交给产品和 UI 维度共用。应用依赖数据时，空库的界面审不出东西：在 `<临时路径>` 下建一份合成数据（参照项目测试里写入数据的方式，覆盖主要实体和几种状态），只通过环境变量、启动参数或 `<临时路径>` 下的配置让应用指向它。写入数据之前先确认应用实际生效的数据位置在 `<临时路径>` 内（很多框架默认把库放在仓库里，或忽略环境变量）。以下情况先问用户，用户不同意就改为静态审查：需要改项目文件、需要复制用户的 `.env` 等本地配置、要在用户已有的数据库服务上建库、应用会连非本地服务。不连用户的真实数据，不用真实账号；凭据类文件放在 `<临时路径>`，新建的库和数据登记到 progress.md，收尾时清理。

用几行话告诉用户：画像要点、审查范围与维度、会不会实际运行应用、成本预估；提问偏好为"可提问"时，说明"需要业务判断的问题会在审查结束前集中问一次"。授权仍是"待问"时在这里问一句，但不必等回答，继续往下审。

### 2. 分维度审查

先按 `assets/brief-common.md` 把各维度共用的要求填成 `<AUDIT>/brief-common.md`（被审 commit、审查位置、画像与基线路径、范围、问题格式、严重度、只读约束、产出方式），每个维度的 brief 只引用它的路径、再加本维度特有的内容。这样各维度标准一致，也省 token。

每个维度派一个 reviewer 并行审查，维度 brief 再给：该维度审查指南（`references/product.md`、`references/ui.md`、`references/code.md`、`references/tests.md`）的绝对路径（产品维度同时给 code.md，用于判定"没有调用方"）、编号前缀、结果文件 `<AUDIT>/findings-<维度>.md`、本维度能否操作本地应用。reviewer 自己把完整问题清单写进结果文件，只返回摘要——主 agent 转述或手抄会走样，也会挤占上下文。每个 reviewer 返回后，主 agent 检查结果文件存在、条数与摘要一致；它没能写文件时，让它在回复里返回完整清单，主 agent 原样存进结果文件。

产品和 UI 维度共用同一个应用（常常也是同一个浏览器实例），并行操作会互相改掉页面和数据：同一时间只让一个维度实际操作应用：通常由 UI 维度操作；产品维度以走查代码为主，在结果里列出需要实际操作确认的点，UI 维度完成后由主 agent 续用产品维度的 subagent 去操作。截图文件名加维度前缀。质证阶段并行的 verifier 也按同样的规则轮流操作。

不给它别的维度的发现，让每个维度独立判断（brief 里写明不读 `<AUDIT>` 下没列给它的文件）。

需要改动代码才能做的验证（如测试维度的变异验证）由 reviewer 提出候选，主 agent 在第 3 步汇总时按 `references/tests.md` 执行，结果写进对应条目的依据。

环境里没有 subagent 时，主 agent 按维度依次自己审，一个维度审完再进入下一个。

### 3. 内部评审，达成一致

按 `references/consensus.md` 执行：汇总去重 → 全范围质证 → 裁决 → 只对有分歧的条目复核，直到每条问题都有终态，最多 3 轮 → 写报告之前，把需要用户判断的条目集中问一次（提问偏好为"不打断"时跳过）。报告里留给用户的待决事项越少，后续修复越不会卡住。

这一步决定报告的可信度，不要因为条目多就跳过。

### 4. 产出报告

按 `assets/report-template.md` 把报告写到 `<AUDIT>/report.md`（不要写进用户的工作树；入库时第 5 步再复制进临时 worktree）。报告语言跟随项目（项目文档是中文或无明确语言时用中文）。仓库按公开处理时，安全类条目在这里就按 `references/pr.md`「敏感内容」写成占位，细节写进 `<AUDIT>/security.md`。报告里的位置一律写相对仓库根的路径，不出现本机绝对路径（审查位置、`<AUDIT>`、临时目录）。报告开头的"修复约定"一节必须保留（非 git 项目除外）：后续修复可能在没有加载本 skill 的会话里进行，约定要随报告走。

### 5. 提交 PR/MR

按 `references/pr.md` 执行：在一个新的临时 worktree 里从被审 commit 建 `<audit 分支>` 并提交报告（报告不入库时——项目约定不允许或用户要求——提交一个空提交，报告放进 PR/MR 评论，见 `references/pr.md`「报告放在哪里」；用户的工作树始终不切分支），获授权时推送并开以第 1 步确定的目标分支为目标的 **draft** PR/MR，描述里放可勾选的问题清单，写明"后续修复都在此 PR/MR 中完成"。到这一步授权仍是"待问"就再问一次（第 3 步集中提问时已一并问过的不再问），没有回答按未授权处理；有敏感信息公开风险时，即使已授权也先向用户确认（见 `references/pr.md`「敏感内容」）。未授权、没有 remote 或没有可用 CLI 时，停在本地提交，并把 PR 描述交给用户。不推默认分支，不 force push，不合入。

### 6. 收尾

- 删除本流程建的临时 worktree（`git worktree remove`），停掉本流程启动的本地服务和模拟器，删掉登记的临时文件和合成数据（含在已有数据库服务上新建的库）。
- `<AUDIT>` 保留（已被 git 忽略），里面的过程记录后续修复时可参照；报告本身以 audit 分支（不入库时为 PR/MR 评论）里的版本为准；未开 PR/MR 时就是 `<AUDIT>/report.md`。
- 给用户的总结只说：问题总数和严重度分布、最该先修的 3–5 条、仍待用户决定的点、报告和 PR/MR 链接、`<AUDIT>` 位置（并提一句已在 `.git/info/exclude` 里忽略 `.audit/`）。不把整份报告贴进对话。

## 问题格式

每条问题一段，字段齐全：

```
### [CD-03] 订单状态在三处各自维护，存在不一致窗口
- 维度：代码 | 严重度：S1 | 工作量：M | 置信度：高 | 状态：已确认
- 位置：src/order/service.ts:120-188，src/order/store.ts:45，src/api/order.ts:77
- 现象：……（客观描述，不带结论）
- 依据：……（为什么这是问题：引用代码、复现步骤、命令输出、违反的原则或项目自身约定）
- 影响：……（对用户 / 维护 / 风险的具体后果）
- 修复建议：……（改成什么样；有多个方案时给推荐项和取舍）
```

编号前缀：PD 产品、UI 界面与交互、CD 代码、TS 测试。编号在审查时由各维度给出，此后保持不变（合并、驳回留下的空号不补），这样证据文件、质证记录和报告能直接对上；只有编号冲突时才重编，并在 consensus-log 里记新旧对照。合并后跨维度的问题用主维度前缀，在"维度"里列出全部相关维度。工作量：S（半天以内）、M（一到两天）、L（更多，建议拆成子项）。

性能、体积、耗时这类优化条目，在"影响"里写收益并注明依据。依据只能是实测数据（基线输出、测试耗时、项目已有构建产物时的体积），或能数出来的事实并写出算式（如每次请求的查询数从 n 降到 1）。两者都没有时只写机制和量级，不写百分比；连机制和量级都说不清、改动又会增加复杂度的，不报。

需要业务判断才能定的条目（某功能该不该留、某行为是否有意为之），审查者在条目里写"待问用户：问题；候选方案；推荐项"，不自己去问用户，由主 agent 在第 3 步汇总后统一问。

## 严重度

- **S0 阻断**：核心路径走不通、数据丢失或损坏、安全漏洞、测试造假掩盖了真实失败。应立即修；经用户同意可以单独走 hotfix PR，在清单里注明去向。
- **S1 重要**：明显伤害用户体验或可维护性、已知会出错的潜在风险、重要路径没有测试保护、明显违背产品目标的设计。本 PR/MR 内修。
- **S2 一般**：改了更好，影响有限或局部。可在本 PR/MR 中顺手修，也可另排，另排时注明去向。
- **S3 观察**：值得留意的趋势或假设，暂不需要行动，或需要更多信息（如使用数据）才能判断。

## 状态

| 状态 | 含义 | 进报告正文 |
|---|---|---|
| 待质证 | 审查阶段的初始状态 | 否，质证后改为终态 |
| 已确认 | 质证通过 | 是 |
| 存在分歧 | 两轮来回仍无新证据，问过用户仍未定（或未能问） | 是，列入"需要决策" |
| 待产品确认 | 需要业务信息才能判断、尚未得到用户决定（含待问、用户表示暂时无法判断、没有答复、超出提问上限未问、提问偏好为"不打断"） | 是，列入"需要决策" |
| 接受风险 | 安全漏洞或数据丢失、损坏类的 S0/S1，用户确认是有意设计并接受风险 | 是，注明用户的确认；不进修复清单，不计入"S0/S1 全部处理" |
| 未充分质证 | 达到轮数上限时仍未裁定 | 是，列入"需要决策"并单独标注 |
| 已驳回 | 被反证推翻，或用户确认是有意设计（安全漏洞或数据丢失、损坏类的 S0/S1 除外，见"接受风险"） | 否，只进附录 |
| 已修复 / 误判 / 另排 | 后续修复阶段更新 | 报告入库时原地更新状态并注明提交或原因；不入库时只更新 PR/MR 清单并评论 |

拿不出依据、只是怀疑的点不作为问题条目，可以写进报告"审查范围与局限"作为待查线索。

## 后续修复

用户之后要求按报告修复时：在 audit 分支上修（已合入或关闭则问用户）；用户工作区有未提交改动时不要直接切分支，先问用户，或用 `git worktree add <持久路径> <audit 分支>` 在单独的工作树里修（修复可能持续多天，不要放在系统临时目录；默认放在仓库同级的 `<仓库名>-audit-fix/`，或问用户）。按报告开头的"修复约定"执行。报告不入库时，报告全文在 PR/MR 评论里，修复进度以 PR/MR 描述中的清单为准；还没开 PR/MR 时，进度记在 `<AUDIT>/pr-body.md` 的清单里，开 PR/MR 时随之带上。基线分支有更新时用 merge 同步，不 rebase、不 force push。用 devflow 之类的开发流程做修复时，其中"切分支、开 PR、合入、删分支"的步骤以本 PR/MR 为准，其余照常。
