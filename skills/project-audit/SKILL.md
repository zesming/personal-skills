# project-audit

被委派执行子任务的 subagent 不使用本 skill，直接完成 brief 里的任务。

## 环境与约定

- 本 skill 同时用于 Claude Code 和 Codex。文中的审查者（reviewer）、verifier 指角色，不是 agent 名字：从当前环境里选最匹配的 subagent，没有就用通用 subagent，并把角色要求写进 brief。
- 审查和质证 subagent 要能往 `<AUDIT>` 写文件（证据，以及宿主允许时的结果文件）：被定义为完全只读、不能写文件的 agent 不选，改用通用 subagent，把只读约束写进 brief。派审查类 subagent 时不让它继承当前对话（Codex 中用 `fork_turns="none"`）。
- 续用已有 subagent：Claude Code 用 SendMessage，Codex 用 `followup_task`（`target` 填派出时的 `task_name`）；不支持续用时重新派一个，把需要的上下文写进 brief。为此派出后把 subagent ID 记入 progress.md。
- 任何 subagent 因用量上限、超时等中断时，续用同一个让它从中断处继续，并告诉它判断进度只看它自己已有的结果和临时目录，不翻 `<AUDIT>` 下的其他文件。不要重新派一个从头来过；用量上限通常要等额度恢复，立即重试多半还会失败，拿不准就问用户。只能改派新 subagent 时，让它接着已有的结果文件往下写，不要覆盖；宿主不允许 subagent 写结果文件时，把已有结果文件列给它，让它在回复里只返回新增部分，由主 agent 追加。
- 平台 CLI / API（托管平台、PR/MR）：用该平台在本机可用的 CLI 或 API，先确认已认证；先看 help 或文档，不猜命令和参数，拿不准时把命令交给用户执行。以非交互方式调用：正文从文件传入，不打开编辑器或交互菜单；只用 CLI 已有的认证或用户提供的方式，不读取、不输出凭据；不自行加参数绕过安全策略确认（跳过创建确认这类交互提示不在此列）。传 PR/MR 链接或显式指定仓库，不依赖当前目录的 origin；自建或企业实例要指定主机。
- 路径：`references/…`、`assets/…` 都相对本 skill 根目录；`<AUDIT>` 指第 1 步在用户原仓库根目录建的工作目录 `.audit/<日期><后缀>/` 的绝对路径，主 agent 自己引用和传给 subagent 时都用绝对路径；`<临时路径>` 指系统临时目录下新建的目录，不放在仓库里。

## 这个 skill 产出什么

一份经过质证的问题清单，不是修复。审查阶段不改项目代码；产物只有：工作目录里的过程记录、审查报告（按项目约定入库，或只放在 PR/MR 里）、一个 draft PR/MR。后续修复提交到这个 PR/MR 的分支上。审的是一个 PR/MR 时例外：问题评论在这个 PR/MR 上并给出审查结论，不另写报告、不开 PR/MR。

## 模式

- **全量审查**（默认）：审整个项目的某个版本（可只审指定维度或模块），按下文流程执行。
- **范围审查**：用户指定了一个 PR/MR、两个提交之间（A..B）或一段时间（某日期以来、最近 N 天）的改动时使用。先读 `references/scope.md`（审 PR/MR 时另读 `references/scope-pr.md`），它们按步骤写明替换下文哪些规则；没写到的照下文执行。

## 原则

- **证据优先**：每条问题都要有可核对的依据——`文件:行号`、可复现的操作路径、截图、命令输出、提交记录。拿不出依据的不算问题。
- **先理解意图，再判断冗余**：说一个功能多余、一段设计不合理之前，先读 README、文档、提交历史和相关 issue，弄清它为什么存在。没有使用数据时，"冗余"只是假设，要标明置信度和验证方式。
- **偏向做减法**：修复建议优先考虑删除、合并、简化，其次才是新增。每条建议说清改完的样子，而不是"建议优化"。
- **抓大放小**：报告的价值在于让人知道先修什么。同一根因的多处表现合并成一条；风格偏好、无实际影响的写法不进清单。宁可 20 条都站得住，不要 80 条里混着一半噪音。
- **诚实标注覆盖范围**：写清审了什么、没审什么、用了什么手段（静态阅读 / 运行测试 / 实际操作应用），不把抽样结论说成全量结论。
- **不扩散敏感信息**：密钥、凭据、个人数据只写位置和类型，不写值；未修复的安全类问题细节不发到公开位置；入库前的检查见 `references/pr.md`「敏感内容」。

## 流程

### 1. 摸底与定范围

**接续**：先看仓库根目录下有没有未完成的 `.audit/*/progress.md`，有就问用户是否从记录的步骤接着做；`questions.md` 里有状态为"已发未回"的问题（见 `references/consensus.md`「向用户确认」）时，在同一条消息里重新列出它们，其他的不再问。

**确认范围与授权**：
- 用户只要求某些维度或某个模块（"审一下测试""看看支付模块的技术债"）时，只审指定部分，其余流程不变。
- 本地 audit 分支和提交总会做；需要授权的是**推送分支和开 draft PR/MR**。用户显式调用本 skill（`/project-audit`、`$project-audit`）或在请求中明确要求开 PR/MR、推送审查结果，视为已授权，除非用户另有说明（如"别开 PR"）；否则记为"待问"。
- 用户没有明确要求审查或出报告、只是由宽泛说法触发时（"看看项目有什么问题"；"全面审查/审计这个项目"这类已明确要审查的不算），全量审查代价不小：只做只读摸底（读文档、看结构），用一条消息说明打算审的范围和维度，并一并问是否推送开 PR/MR，**等用户确认后**再建工作目录、worktree、跑基线和派 subagent。用户不继续就到此为止，不留下任何改动。

**确认环境与被审版本**（报告行号、PR 基线都以此为准，在这里一次定死）：
- 不是 git 仓库：照常审查并写报告，跳过第 5 步，报告留在工作目录交给用户，报告里删去"修复约定"一节。
- 记录 remote（判断托管平台）。有多个 remote 或仓库是 fork 时问用户推到哪里（`<推送 remote>`）、PR/MR 开到哪个仓库（`<目标 remote>`）；只有一个 remote 时两者相同。下面的远端比较以 `<目标 remote>` 为准。没有 remote 时跳过远端相关检查，第 5 步只做本地提交。查仓库可见性和是否为 fork（用平台 CLI / API，见「环境与约定」）：
  - 只有"仅项目成员可见"算 private；公开、公司或实例内部可见都按公开处理——内部可见时，安全细节写进报告就等于对全公司公开。查不出来时，答复前也一律按公开处理。
  - 查不出来时问用户，问法写明后果（如"仓库是否只有项目成员可见？确认后安全类细节会写进报告和 PR/MR"）：本步有要等回答的提问就并进第一条，没有就放进本步结尾的摘要，不等回答继续审；仍未答的在第 3 步集中提问时一并问，那时也没明确回答就记"已问未答"。
- 基线分支：当前在默认分支上就用它；在其他分支上时问用户审哪个分支。
- 被审 commit = `git rev-parse <基线分支>`（不用 `HEAD`）。先用 `git ls-remote --exit-code --heads <目标 remote> <基线分支>` 确认远端分支存在（本地跟踪引用可能已过期，不能代替），再 `git fetch --prune <目标 remote>` 后对比：
  - 本地领先（`git rev-list --count <目标 remote>/<基线分支>..<被审 commit>` > 0）：告诉用户，让用户选择改审远端版本，还是同意这些提交随 audit 分支一起推送。
  - 本地落后（反向计数 > 0）：告诉用户，问是否改审远端最新版本。
  - 基线分支在远端不存在：同样视为"含远端没有的提交"，让用户选择换一个远端已有的分支作为审查和 PR/MR 目标，或只做本地提交、不推送。
  - 用户换了分支或改审远端版本时，对新的被审 commit 重新做上述对比。
  - 用户选择之前不推送任何东西。
- 审查位置：被审 commit 就是当前 `HEAD` 且工作区干净时，直接在仓库里审；否则用 `git worktree add --detach <临时路径> <被审 commit>` 在干净副本里审（不碰用户未提交的改动；依赖需要重新安装时先问用户，装之前先按「跑基线」备份 config）。

**读项目约定**：AGENTS.md、CLAUDE.md、CONTRIBUTING、提交与分支命名规范等。其中关于代码、产品和测试的约定是审查标准（"违反项目自身约定"是有力的依据）；提交、分支、PR 规范只用于交付——决定报告是否入库（见 `references/pr.md`「报告放在哪里」）、audit 分支名（项目规定了分支前缀时，在 `audit/<日期>` 前按约定加前缀）和提交信息，不作为审查依据。这些文件本身也在代码维度接受审查（见 `references/code.md`「agent 指令文件」），经质证确认过时或矛盾的约定不再作为判定依据。结论写进画像。同时用 `git ls-tree -r --name-only <被审 commit>` 列出 agent 指令文件（文件名见 `references/code.md`「agent 指令文件」；不用 `git ls-files`，它列的是当前检出版本），列表写进画像，交给代码维度。

在**用户原仓库根目录**建工作目录 `<AUDIT>`。后缀在这里一次定下：`.audit/<YYYY-MM-DD>/` 目录、本地分支 `<前缀>audit/<YYYY-MM-DD>`（无前缀约定时为空）、远端同名分支（`git ls-remote --heads`）任一已存在（且不是要接续的），就统一加 `-2` 等后缀，目录、分支、报告文件名共用。最终分支名记为 `<audit 分支>`，写入 progress.md，后文都用它。`<AUDIT>` 不能放进任何临时 worktree，否则删 worktree 时会被一起删掉。`git rev-parse --git-path info/exclude` 指向的文件还没忽略 `.audit/` 时追加这一条，不改项目的 `.gitignore`。按 `assets/progress.md` 建 `progress.md`，把上面确认的环境、被审版本、PR/MR 目标分支、用户的选择和项目约定记进去，之后每完成一步更新。

**建立项目画像**，写入 `<AUDIT>/profile.md`：
- 产品定位与目标用户、产品要解决的核心问题（来自 README、文档、首页文案、代码中的命名）
- 功能清单：从路由、菜单、命令、API 端点、配置开关、文档里归纳
- 核心用户路径 3–7 条（如"首次使用 → 完成第一个核心任务"）
- 技术栈、模块地图、入口、构建与运行方式
- 测试体系：框架、目录、CI 配置、是否有覆盖率配置
- 项目约定：影响审查标准和报告交付的条目
- 热点：`git log --since=6.months --format= --name-only | sort | uniq -c | sort -rn | head -30` 找改动最频繁的文件

**定维度**：四个维度默认都审，按项目形态调整：
- 没有图形界面（库、CLI、后端服务）：UI 维度改为"接口 / CLI / 配置的易用性"，并入产品维度一起审。
- 几乎没有测试：测试维度聚焦"哪些高风险路径最该先补测试"，不逐条列"未覆盖"。

**定覆盖面**：代码量大（粗略超过 5 万行）或是 monorepo 时，按"核心用户路径涉及的模块 + 改动热点 + 复杂度最高的模块"选范围，其余列为未覆盖。monorepo 里看不出用户关心哪个子项目时先问。

**估算成本**：每个审查维度派一个 subagent，质证再按条目量派一到数个，另有最多两轮复核；在中等规模项目上每个通常要十几分钟、数十万 token。据此粗估总量，放进本步结尾给用户的摘要。达到上面"定覆盖面"的门槛（大项目或 monorepo）时，在跑基线**之前**把范围和预估告诉用户，等用户选择全量、缩小范围、按维度分批派发（分批只是派发顺序，所有维度审完才进入第 3 步），或省用量（见下）。

**模型与推理档位**：环境允许按 subagent 指定模型或推理档位时，审查和质证用不低于主 agent 当前的配置。用户要求省用量（在请求里或任何时候）时，先建议缩小范围或分批；确实要降档，只降第 2 步的审查 subagent，质证不降——它决定报告的可信度。降档情况记入 progress.md 和报告的"审查手段"。不写死具体模型名；环境不支持按 subagent 指定时不处理。预定义的 subagent 可能固定了较低的模型，拿不准时选能继承主 agent 配置的通用 subagent。

**提问偏好**：用户或调用方明确说过"跑完再看""别打断"、或声明是非交互运行时，记为"不打断"：第 3 步不集中提问，需要用户判断的条目直接保留"待产品确认"；流程里其他需要问用户的点，取不产生外部副作用的选项（如不推送、不开 PR/MR）；各选项都没有外部副作用时（如审哪个分支或子项目、报告是否入库），取推荐项或更保守的一项。这些取舍记入 progress.md 和报告的"局限"。不要靠猜测判断环境是否可交互；没有说明时记为"可提问"。

**跑基线**（整套测试、构建由主 agent 在审查位置统一跑，避免多个 subagent 抢端口和构建目录；基线跑完后审查者可以跑聚焦测试，见 `assets/brief-common.md`「只读约束」）：
- 先读测试配置和脚本。需要真实凭据、连接非本地数据库或外部服务的套件，先问用户再跑。
- 装依赖或跑测试之前，按 `references/consensus.md`「保护用户仓库的 git 配置」备份 config；跑测试的命令或脚本里先 `unset $(git rev-parse --local-env-vars)`，之后按那一节对比：测试会继承 git 设置的 `GIT_DIR` 改写用户仓库，worktree 也和用户仓库共用 config。
- 跑全部测试，不只默认入口：各子包的、CI 调用的、发版前或全量入口都跑；没有任何入口覆盖的测试目录，用测试框架按目录跑一次；覆盖情况写进 `<AUDIT>/baseline/` 的摘要和画像的"测试体系"。耗时长的放后台跑，不等它跑完就派审查者。另跑项目已配置的覆盖率、项目已有的 lint / 复杂度工具；输出存到 `<AUDIT>/baseline/`，覆盖率等报告尽量直接指定输出到那里。跑前跑后各看一次 `git status`，测试在仓库里留下的产物要清理掉。
- 只用项目自带或本机已装的工具；需要联网安装依赖时先问用户。跑不起来就如实记录原因。
- 需要审 UI 且能运行时，由主 agent 启动一次本地应用，把地址交给产品和 UI 维度共用：
  - 应用依赖数据时，空库的界面审不出东西：在 `<临时路径>` 下建一份合成数据（参照项目测试里写入数据的方式，覆盖主要实体和几种状态），只通过环境变量、启动参数或 `<临时路径>` 下的配置让应用指向它。写入数据之前先确认应用实际生效的数据位置在 `<临时路径>` 内（很多框架默认把库放在仓库里，或忽略环境变量）。
  - 正式启动方式被项目约定禁止、或会落到下一条要问用户的情况时，先找项目里的测试 harness、mock 服务或 demo 模式，都没有再问用户。用 harness 时先读它的实现，把它与生产的差异（没接的子系统、写死的返回、fixture 缺的字段）写进 brief-common 的"本地应用"一行和报告"局限"。
  - 以下情况先问用户，用户不同意就改为静态审查：需要改项目文件、需要复制用户的 `.env` 等本地配置、要在用户已有的数据库服务上建库、应用会连非本地服务。
  - 不连用户的真实数据，不用真实账号；凭据类文件放在 `<临时路径>`，新建的库和数据登记到 progress.md，收尾时清理。

用几行话告诉用户：画像要点、审查范围与维度、会不会实际运行应用、成本预估；提问偏好为"可提问"时，说明"需要业务判断的问题会在审查结束前集中问一次"。授权或可见性仍是"待问"时在这里问一句，但不必等回答，继续往下审。

### 2. 分维度审查

先按 `assets/brief-common.md` 把各维度共用的要求填成 `<AUDIT>/brief-common.md`，每个维度的 brief 只引用它的路径、再加本维度特有的内容，这样各维度标准一致，也省 token。填写时保留模板各节原文，只替换尖括号占位。项目特有的要求追加在末尾，不得与模板相抵，确需收紧（如项目约定限制并行跑测试）时写明原因——模板里的每一句都对应过实际踩过的坑，改写或删掉会让审查者漏查或少验证。

每个维度派一个审查者并行审查，维度 brief 再给：该维度审查指南（`references/product.md`、`references/ui.md`、`references/code.md`、`references/tests.md`）的绝对路径（产品维度同时给 code.md，用于判定"没有调用方"）、编号前缀、结果文件 `<AUDIT>/findings-<维度>.md`、本维度能否操作本地应用。

- 审查者自己把完整问题清单写进结果文件，只返回摘要——主 agent 转述或手抄会走样，也会挤占上下文。
- 宿主规定 subagent 只能用文本返回结果时（如 Claude Code 会拒绝 subagent 写 findings、report 这类文件），派出时就在 brief-common「产出」里选文本返回的写法，被拒后不换文件名重试。这种情况以及它只是没能写成文件时，让它在回复里返回完整清单，主 agent 原样存进结果文件：宿主把 subagent 的输出存成文件时（如 Claude Code 后台 subagent 的输出文件，为此用后台方式派出），用命令从中提取最终回复落盘，不用写文件工具重写。
- 每个审查者返回后，主 agent 核对：结果文件存在、条数与摘要一致，覆盖说明回应了 brief 点名的检查项（代码维度至少包括列表里的每个指令文件）。漏掉的续用同一个 subagent 补上，确实做不了的写进"未覆盖"。

产品和 UI 维度共用同一个应用（常常也是同一个浏览器实例），并行操作会互相改掉页面和数据。同一时间只让一个维度实际操作应用，通常由 UI 维度操作；产品维度以走查代码为主，在结果里列出需要实际操作确认的点，UI 维度完成后由主 agent 续用产品维度的 subagent 去操作。截图文件名加维度前缀。质证阶段并行的 verifier 也按同样的规则轮流操作。

不给审查者别的维度的发现，让每个维度独立判断。基线仍在跑时派出的，跑完后续用各审查者，告知结果位置和可以跑聚焦测试了。审查者提出的需要改代码或加测试文件的验证，由主 agent 在第 3 步按 `references/consensus.md` 第 1 步处理。

环境里没有 subagent 时，主 agent 按维度依次自己审，一个维度审完再进入下一个。

### 3. 内部评审，达成一致

按 `references/consensus.md` 执行：汇总去重 → 全范围质证 → 裁决 → 只对有分歧的条目复核，直到每条问题都有终态，最多 3 轮 → 写报告之前，把需要用户判断的条目集中问一次。报告里留给用户的待决事项越少，后续修复越不会卡住。

这一步决定报告的可信度，不要因为条目多就跳过。

### 4. 产出报告

按 `assets/report-template.md` 把报告写到 `<AUDIT>/report.md`（不要写进用户的工作树；入库时第 5 步再复制进临时 worktree）。报告语言跟随项目（项目文档是中文或无明确语言时用中文）。

- 条目多（约 30 条以上）时不要一次写出整份报告：每个维度的终态条目各写一个 `<AUDIT>/final-<前缀>.md`（报告格式，排好序），其余章节另写一个文件，再用放在 `<AUDIT>` 里的脚本按模板顺序拼成 report.md；统计表和 PR/MR 描述里的清单也由脚本从条目字段生成。
- 仓库按公开处理时，安全类条目在这里就按 `references/pr.md`「敏感内容」写成占位，细节写进 `<AUDIT>/security.md`。
- 位置一律写相对仓库根的路径，不出现本机绝对路径（审查位置、`<AUDIT>`、临时目录）。
- 开头的"修复约定"一节必须保留（非 git 项目除外）：后续修复可能在没有加载本 skill 的会话里进行，约定要随报告走。

### 5. 提交 PR/MR

按 `references/pr.md` 执行：在一个新的临时 worktree 里从被审 commit 建 `<audit 分支>` 并提交报告（报告不入库时——项目约定不允许或用户要求——提交一个空提交，报告放进 PR/MR 评论；用户的工作树始终不切分支）。获授权时推送并开以第 1 步确定的目标分支为目标的 **draft** PR/MR，描述里放可勾选的问题清单，写明"后续修复都在此 PR/MR 中完成"；有公开风险时即使已授权，也要先过推送前确认。授权仍待问、推送前确认、无法提交时怎么做，见 pr.md「前置检查」「敏感内容」「无法提交时」。不推默认分支，不 force push，不合入。

### 6. 收尾

- 删除本流程建的临时 worktree（`git worktree remove`），停掉本流程启动的本地服务和模拟器，删掉登记的临时文件和合成数据（含在已有数据库服务上新建的库）。
- `<AUDIT>` 保留（已被 git 忽略），里面的过程记录后续修复时可参照；报告本身以 audit 分支（不入库时为 PR/MR 评论）里的版本为准；未开 PR/MR 时就是 `<AUDIT>/report.md`。
- 给用户的总结只说：问题总数和严重度分布、最该先修的 3–5 条、仍待用户决定的点、报告和 PR/MR 链接、`<AUDIT>` 位置（并提一句已在 `.git/info/exclude` 里忽略 `.audit/`）。不把整份报告贴进对话。

## 问题格式与严重度

条目格式、编号前缀、工作量和严重度定义在 `assets/brief-common.md`「问题格式」「严重度」：审查者和 verifier 拿到的就是这份，主 agent 汇总、裁决、写报告时也按它。编号冲突和合并后的编号见 `references/consensus.md`「编号」。

## 状态

| 状态 | 含义 | 进报告正文 |
|---|---|---|
| 待质证 | 审查阶段的初始状态 | 否，质证后改为终态 |
| 已确认 | 质证通过 | 是 |
| 存在分歧 | 两轮来回仍无新证据，问过用户仍未定（或未能问） | 是，列入"需要决策" |
| 待产品确认 | 需要业务信息才能判断、尚未得到用户决定（含待问、用户表示暂时无法判断、没有答复、超出提问上限未问、提问偏好为"不打断"） | 是，列入"需要决策" |
| 接受风险 | 安全漏洞或数据丢失、损坏类的 S0/S1，用户确认是有意设计并接受风险 | 是，注明用户的确认；不进修复清单，不计入"S0/S1 全部处理" |
| 未充分质证 | 达到轮数上限时仍未裁定 | 是，列入"需要决策"并单独标注 |
| 已驳回 | 被反证推翻，或用户确认是有意设计（安全漏洞或数据丢失、损坏类的 S0/S1 除外，见"接受风险"） | 否，只进附录 |
| 已修复 / 误判 / 另排 | 后续修复阶段更新 | 报告入库时原地更新状态并注明提交或原因；不入库时只更新 PR/MR 清单并评论 |

## 后续修复

用户之后要求按报告修复时：在 audit 分支上修（已合入或关闭则问用户）；用户工作区有未提交改动时不要直接切分支，先问用户，或用 `git worktree add <持久路径> <audit 分支>` 在单独的工作树里修（修复可能持续多天，不要放在系统临时目录；默认放在仓库同级的 `<仓库名>-audit-fix/`，或问用户）。按报告开头的"修复约定"执行（含不入库时的进度记法和 merge 同步规则）。用 devflow 之类的开发流程做修复时，其中"切分支、开 PR、合入、删分支"的步骤以本 PR/MR 为准，其余照常。
