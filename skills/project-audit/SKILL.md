# project-audit

被委派执行子任务的 subagent 不使用本 skill，直接完成 brief 里的任务。

## 环境与约定

- 选能写入 `<AUDIT>` 保存证据的审查者和 verifier。角色完全只读时，选有相应能力的通用 subagent，在 brief 中写明只读边界。新派审查类 subagent 从干净上下文开始，只接收审查所需材料。环境允许选择时，显式选择不继承会话。
- 派出后将可用于续用的标识记入 progress.md。中断后让原 subagent 只凭自己的结果和临时目录接续。用量耗尽时等额度恢复，拿不准就问用户。只能换人时，在 brief 给出已有结果，让接手者追加；环境限制写入时由主 agent 追加返回的新增结果。
- **平台 CLI / API**：先确认已认证并查用法，拿不准时把命令交给用户。用 PR/MR 链接或显式指定仓库和企业主机，正文从文件传入，非交互执行。使用已有认证或用户指定的方式，不读写或输出凭据，也不绕过安全确认。创建命令的普通交互提示可跳过。
- **路径**：`references/…`、`assets/…` 相对 skill 根目录。`<AUDIT>` 是原仓库根目录的 `.audit/<日期><后缀>/`，使用及传给 subagent 时写绝对路径。`<临时路径>` 是仓库外新建的系统临时目录。

## 这个 skill 产出什么

交付经过质证的问题清单，审查阶段保持项目实现只读。报告可留在本地，按项目约定入库或发成 PR/MR 评论。获授权后用 draft PR/MR 跟踪修复。审已有 PR/MR 时，交付其行内评论和审查结论。

## 模式

- **全量审查**（默认）：审指定版本的项目，找出缺陷，并从全局判断哪些内容、功能、流程、实现和测试可精简。用户指定维度或模块时，以指定范围为准。
- **范围审查**：审一个 PR/MR、提交区间（A..B）或一段时间内的改动及其直接涉及的问题。先读 `references/scope.md`，审 PR/MR 另读 `references/scope-pr.md`。按其中列出的步骤覆盖本文件的对应规则。

## 原则

- **证据优先**：每条问题都要有可核对的依据——`文件:行号`、可复现的操作路径、截图、命令输出、提交记录。拿不出依据的不算问题。
- **先核对用途再建议精简**：结合文档、实现、提交和 issue 了解服务对象、场景与约束。重复可以靠对照确认；判断功能无人使用要有调用、使用或业务证据，证据不足则标明待确认。
- **优先删除、合并或简化**：只报有实际影响的发现。精简建议要写明保留的行为、承接处和验证方法，规则见 `assets/brief-common.md`。同一根因合并成一条。
- **诚实标注覆盖范围**：写清审了什么、没审什么、用了什么手段（静态阅读 / 运行测试 / 实际操作应用），不把抽样结论说成全量结论。
- **不扩散敏感信息**：密钥、凭据、个人数据只写位置和类型，不写值；未修复的安全类问题细节不发到公开位置；入库前的检查见 `references/pr.md`「敏感内容」。

## 流程

### 1. 摸底与定范围

**接续**：检查仓库根目录的 `.audit/*/progress.md`。有未完成审查时，询问是否接续，并附 `questions.md` 中仍为「已发未回」的问题。

**确认范围与授权**：
- 用户指定维度、模块或文档时，只审指定内容。文档按下文的职责分工分派。
- 本地 audit 分支与提交按第 5 步处理。用户显式调用本 skill，或明确要求推送审查结果、开 PR/MR 时，视为已授权推送并开 draft PR/MR。用户另有限制时从其要求。其余记为「待问」。
- 「看看项目有什么问题」等宽泛请求，先只读摸底。一次说明计划范围和维度，并询问是否继续、是否推送开 PR/MR。用户确认继续后再创建工作目录和 worktree、跑基线、派 subagent。

**确认环境与被审版本**（报告行号、PR 基线都以此为准，在这里一次定死）：
- 不是 git 仓库：照常审查并写报告，跳过第 5 步，报告留在工作目录交给用户，报告里删去"修复约定"一节。
- 记录托管平台，并用 CLI / API 核查可见性和是否为 fork。只有一个 remote 且并非 fork 时，它同时是推送和目标 remote。多个 remote 或 fork 时请用户选这两者。远端比较以目标 remote 为准。无 remote 时跳过远端检查，第 5 步只做本地提交。
- 仅项目成员可见才按 private 处理。公开、组织或实例内可见，以及可见性未知时，都按公开处理。未知时并入本步提问或摘要，说明确认 private 后安全细节会写入报告和 PR/MR。可见性单独待答时继续审查。第 3 步集中提问后仍未知，记为「已问未答」。
- 基线分支：当前在默认分支上就用它；在其他分支上时问用户审哪个分支。
- 被审 commit = `git rev-parse <基线分支>`（不用 `HEAD`）。先用 `git ls-remote --exit-code --heads <目标 remote> <基线分支>` 确认远端分支存在（本地跟踪引用可能已过期，不能代替），再 `git fetch --prune <目标 remote>` 后对比：
  - 本地领先（`git rev-list --count <目标 remote>/<基线分支>..<被审 commit>` > 0）：告诉用户，让用户选择改审远端版本，还是同意这些提交随 audit 分支一起推送。
  - 本地落后（反向计数 > 0）：告诉用户，问是否改审远端最新版本。
  - 基线分支在远端不存在：同样视为"含远端没有的提交"，让用户选择换一个远端已有的分支作为审查和 PR/MR 目标，或只做本地提交、不推送。
  - 用户换了分支或改审远端版本时，对新的被审 commit 重新做上述对比。
  - 用户选择之前不推送任何东西。
- 审查位置：被审 commit 就是当前 `HEAD` 且工作区干净时，直接在仓库里审；否则用 `git worktree add --detach <临时路径> <被审 commit>` 在干净副本里审（不碰用户未提交的改动；依赖需要重新安装时先问用户，装之前先按「跑基线」备份 config）。

**读项目约定**：将代码、产品、测试约定写入画像，作为审查标准。提交、分支、PR 规范只用于确定报告交付方式、分支前缀和提交信息。经质证确认过时或矛盾的约定，重新评估依赖它的结论。用 `git ls-tree -r --name-only <被审 commit>` 列出该版本的 agent 指令文件，写进画像并交给代码维度检查。

**建工作目录**：在原仓库根目录创建 `.audit/<YYYY-MM-DD>/`。检查目录和本地、远端同名分支 `<前缀>audit/<YYYY-MM-DD>`（远端用 `git ls-remote --heads`）。任一与其他审查撞名时，目录、分支和报告名统一加 `-2` 等后缀。用 `git rev-parse --git-path info/exclude` 定位本地忽略文件，必要时追加 `.audit/`。按 `assets/progress.md` 记录环境、版本、目标分支、最终分支名、用户决定和项目约定，每完成一步更新。

**建立项目画像**，写入 `<AUDIT>/profile.md`：
- 产品定位与目标用户、产品要解决的核心问题（来自 README、文档、首页文案、代码中的命名）
- 功能清单：从路由、菜单、命令、API 端点、配置开关、文档里归纳
- 核心用户路径 3–7 条（如"首次使用 → 完成第一个核心任务"）
- 技术栈、模块地图、入口、构建与运行方式
- 测试体系：框架、目录、CI 配置、是否有覆盖率配置
- 项目约定：影响审查标准和报告交付的条目
- 热点：`git log --since=6.months --format= --name-only | sort | uniq -c | sort -rn | head -30` 找改动最频繁的文件

**定维度**：默认审产品、UI 与交互、代码、测试。产品负责用户文档，UI 负责界面内文案，代码负责工程文档和 agent 指令。无图形界面时，将接口、CLI、配置的易用性并入产品。几乎没有测试时，优先识别需要保护的高风险路径。

**定覆盖面**：超过约 5 万行或是 monorepo 时，优先审核心路径、改动热点和高复杂度模块，列出未覆盖范围。无法判断用户关心哪个子项目时先问。

**估算成本**：结合覆盖面、派发数、基线和可能的质证轮次估算，写入本步摘要。达到「定覆盖面」门槛时，跑基线前给出范围和预估，等用户选全量、缩小范围、分批派发或省用量。分批时，所有批次完成后再质证。

**模型与推理档位**：宿主支持时，审查和质证至少用主 agent 当前配置。预定义角色配置不明时，选可继承配置的通用角色。用户要求省用量时，优先缩小范围或分批。确需降档时只降发现阶段，并记入进度和报告。

**提问偏好**：默认可提问。用户或调用方明确要求「不打断」或声明非交互时，业务待决项保留为「待产品确认」。其他选择优先取没有外部副作用的方案，再取推荐或更保守的一项。将决定记入进度和报告局限。

**跑基线**（整套测试、构建由主 agent 在审查位置统一跑，避免多个 subagent 抢端口和构建目录；基线跑完后审查者可以跑聚焦测试，见 `assets/brief-common.md`「只读约束」）：
- 先读测试配置和脚本。需要真实凭据、连接非本地数据库或外部服务的套件，先问用户再跑。
- 装依赖或跑测试之前，按 `references/consensus.md`「保护用户仓库的 git 配置」备份 config；跑测试的命令或脚本里先 `unset $(git rev-parse --local-env-vars)`，之后按那一节对比：测试会继承 git 设置的 `GIT_DIR` 改写用户仓库，worktree 也和用户仓库共用 config。
- 跑全部测试，含各子包、CI 和发版入口。没有入口覆盖的测试目录，按框架分目录跑。执行项目已有的覆盖率、lint 和复杂度检查。输出和覆盖摘要写入 `<AUDIT>/baseline/`，画像注明测试入口和覆盖范围。长任务可后台运行，同时派审查者。比较执行前后的 `git status`，清理本流程的测试产物。
- 只用项目自带或本机已装的工具；需要联网安装依赖时先问用户。跑不起来就如实记录原因。
- 需要审 UI 且能运行时，由主 agent 启动一次本地应用，把地址交给产品和 UI 维度共用：
  - 应用需要数据时，在 `<临时路径>` 准备覆盖主要实体和状态的合成数据。通过环境变量、启动参数或临时配置接入，写入前确认实际生效的位置在临时目录内。
  - 正式启动受约束时，先找项目已有的 harness、mock 或 demo。采用时核对与生产的差异，写入共用 brief 的「本地应用」和报告局限。
  - 以下情况先问用户，用户不同意就改为静态审查：需要改项目文件、需要复制用户的 `.env` 等本地配置、要在用户已有的数据库服务上建库、应用会连非本地服务。
  - 不连用户的真实数据，不用真实账号；凭据类文件放在 `<临时路径>`，新建的库和数据登记到 progress.md，收尾时清理。

用几行话告诉用户：画像要点、审查范围与维度、会不会实际运行应用、成本预估；提问偏好为"可提问"时，说明"需要业务判断的问题会在审查结束前集中问一次"。授权或可见性仍是"待问"时在这里问一句，但不必等回答，继续往下审。

### 2. 分维度审查

按 `assets/brief-common.md` 生成 `<AUDIT>/brief-common.md`，只填占位和选择适用的模板分支。项目要求追加在末尾，若需收紧约束，写明原因。各维度 brief 引用共用文件，再补各自要求。

并行派发代码、测试各一人，产品和 UI 合派一人。达到「定覆盖面」门槛时可拆开产品和 UI。brief 给出对应指南（`references/product.md`、`references/ui.md`、`references/code.md`、`references/tests.md`）的绝对路径、编号前缀、结果文件 `<AUDIT>/findings-<维度>.md` 和本维度能否操作应用。产品同时读 code.md 核查间接调用。合派时结果写入 `<AUDIT>/findings-product-ui.md`，各条沿用本维度编号。

- 宿主允许写结果时，由审查者写完整清单并返回摘要。宿主限制写入或写入失败时，审查者在回复里返回全文，主 agent 原样保存。宿主有后台输出文件时，从中提取最终回复。写入被拒时不换文件名重试。
- 主 agent 核对清单、摘要计数和 brief 要求的覆盖说明（含代码维度的每个指令文件）。遗漏交原审查者补查，无法补查的记入「未覆盖」。

共享应用同一时间只交给一个审查者或 verifier 操作。拆派产品和 UI 时，默认 UI 先操作；产品先走查代码，交还应用后再确认需要实操的点。截图文件名加维度前缀。

各维度独立形成发现。基线跑完后，通知已派的审查者读取结果和运行聚焦测试。需要修改代码或新增测试文件的验证，由主 agent 按 `references/consensus.md` 第 1 步处理。

环境里没有 subagent 时，主 agent 按维度依次自己审，一个维度审完再进入下一个。

### 3. 内部评审，达成一致

按 `references/consensus.md` 执行。全量审查由主 agent 在首次质证前沿用户任务做跨维度精简核对。然后质证、裁决，只复核有分歧的条目，最多 3 轮。写报告前集中询问需要用户决定的事项。

### 4. 产出报告

按 `assets/report-template.md` 把报告写到 `<AUDIT>/report.md`（不要写进用户的工作树；入库时第 5 步再复制进临时 worktree）。报告语言跟随项目（项目文档是中文或无明确语言时用中文）。

- 超过约 30 条时，各维度按报告格式生成 `<AUDIT>/final-<前缀>.md`，其他章节另存。用 `<AUDIT>` 中的脚本按模板合成报告，从条目字段生成统计表和 PR/MR 清单。
- 仓库按公开处理时，安全类条目在这里就按 `references/pr.md`「敏感内容」写成占位，细节写进 `<AUDIT>/security.md`。
- 位置一律写相对仓库根的路径，不出现本机绝对路径（审查位置、`<AUDIT>`、临时目录）。
- 开头的"修复约定"一节必须保留（非 git 项目除外）：后续修复可能在没有加载本 skill 的会话里进行，约定要随报告走。

### 5. 提交 PR/MR

按 `references/pr.md` 从被审 commit 建 audit 分支和临时 worktree，在其中提交报告。按约定不入库时，提交空提交，报告用于 PR/MR 评论。授权和公开风险检查通过后，推 audit 分支并开带修复清单的 draft PR/MR。禁止 force push 和合入。

### 6. 收尾

- 删除本流程建的临时 worktree（`git worktree remove`），停掉本流程启动的本地服务和模拟器，删掉登记的临时文件和合成数据（含在已有数据库服务上新建的库）。
- `<AUDIT>` 保留（已被 git 忽略），里面的过程记录后续修复时可参照；报告本身以 audit 分支（不入库时为 PR/MR 评论）里的版本为准；未开 PR/MR 时就是 `<AUDIT>/report.md`。
- 给用户的总结只说：问题总数和严重度分布、最该先修的 3–5 条、仍待用户决定的点、报告和 PR/MR 链接、`<AUDIT>` 位置（并提一句已在 `.git/info/exclude` 里忽略 `.audit/`）。不把整份报告贴进对话。

## 问题格式与严重度

条目格式、编号前缀、工作量和严重度定义在 `assets/brief-common.md`「问题格式」「严重度」：审查者和 verifier 拿到的就是这份，主 agent 汇总、裁决、写报告时也按它。编号冲突和合并后的编号见 `references/consensus.md`「编号」。

## 状态

| 状态 | 含义 | 进报告正文 |
|---|---|---|
| 待质证 | 审查阶段的初始状态 | 否，质证后改为终态 |
| 已确认 | 质证通过 | 是 |
| 存在分歧 | 两轮来回仍无新证据，问过用户仍未定（或未能问） | 是，列入"需要决策" |
| 待产品确认 | 需要业务信息才能判断、尚未得到用户决定（含待问、用户表示暂时无法判断、没有答复、超出提问上限未问、提问偏好为"不打断"） | 是，列入"需要决策" |
| 接受风险 | 安全漏洞或数据丢失、损坏类的 S0/S1，用户确认是有意设计并接受风险 | 是，注明用户的确认；不进修复清单，不计入"S0/S1 全部处理" |
| 未充分质证 | 达到轮数上限时仍未裁定 | 是，列入"需要决策"并单独标注 |
| 已驳回 | 被反证推翻，或用户确认是有意设计（安全漏洞或数据丢失、损坏类的 S0/S1 除外，见"接受风险"） | 否，只进附录 |
| 已修复 / 误判 / 另排 | 后续修复阶段更新 | 报告入库时原地更新状态并注明提交或原因；不入库时只更新 PR/MR 清单并评论 |

## 后续修复

后续按报告修复时，在 audit 分支执行「修复约定」。PR/MR 已合入或关闭时先问用户。用户工作区有未提交改动时，先问用户，或用 `git worktree add <持久路径> <audit 分支>` 隔离，默认路径为仓库同级的 `<仓库名>-audit-fix/`。使用 devflow 等开发流程时，沿用该分支和 PR/MR 的交付、合入和清理约定。
