# 应用图标配置与发布素材

用于把一个已批准的品牌图形可靠地变成三类结果：设计源图、应用包内资源、商店上传图。先判断用户要改的是哪一类，再检查工程的现有图标、目标平台/最低版本、资源限定词、构建工具和商店当前规格。

规则核对日期：2026-09-16。平台文档和商店后台会变化；涉及硬尺寸、格式或新系统外观时，读取 [三平台官方规则](references/platform-rules.md)，并在交付中写明目标 SDK、Xcode/AGP、AGC/Play 规格的适用范围。官方规则、当前工具链行为和项目惯例必须分开叙述。

## 共同工作流

1. 找到目标工程实际使用的入口：应用级配置、主入口 Ability/Activity、资源目录、启动页/关于页引用、商店素材目录和已有导出/校验脚本。按工程现状和官方规则确定路径、命名与工具，不假设不同项目采用相同约定。若已有批准的品牌，保留其主体、颜色和比例；只做合成、等比缩放、编码转换和必要的资源映射。新设计才考虑 imagegen，标准合成不需要 AI。
2. 对多目标或可重复导出，维护一份 manifest，记录各源图和导出图的用途、尺寸、色彩空间、透明度、编码格式、哈希和来源。前景/背景分层源图、包内编译资源、静态合成图和商店图不能只靠文件名互相替代。
3. 设计源图优先保留未裁圆角的正方形画布。分层工作流通常是透明前景 + 完整不透明背景；系统遮罩、圆角、阴影和主题着色由平台在适用表面处理，不能预烘焙到要求系统处理的源图。若某平台明确要求单层资源或商店图，再从同一批准源图生成对应变体。
4. 按任务范围逐个平台配置并验证。只导出/转换资产时，检查导出文件和清单即可；修改包内声明或资源时，再为受影响的平台构建并检查最终包中的资源 ID、尺寸/编码和像素。编译器可以合法地重采样或转码，不能把包内编码尺寸反推为源图硬规则；除非用户要求多平台发布或运行验收，不强制无关平台的完整构建和所有表面运行。
5. 只在用户明确要求时执行上传、提审或发布。普通导出和本地验证不等于商店审核通过；保留构建版本、素材哈希和验证命令。

## 平台路由

- HarmonyOS：读取官方分层图标与 AppGallery 规则。检查 `AppScope/app.json5`、入口模块/Ability 的 `icon`、`layered-image` JSON、`base/phone/tablet` 限定词以及单层启动页图标；应用级和入口级需要同源时，显式核对两者。按目标设备和当前素材规范分别核验源图、包内资源和上传变体。若 SDK 在包内转换图层尺寸或编码，按实际 SDK 行为核对引用和像素，不把包内尺寸误当作源图要求。
- iOS/iPadOS：读取 Apple HIG、Xcode asset catalog 和当前 Icon Composer 说明。`AppIcon` 的 iOS 1,024pt 槽位、系统圆角遮罩、Xcode 自动生成的小尺寸变体、Dark/Tinted 等外观槽位是不同概念；只在目标 SDK/产品确实需要时提供自定义外观，不把 HIG 里的所有外观名称当成每个 target 都必须提供的独立文件。App Store 图标随 Xcode 构建上传，修改已发布图标需要新的 App Store 版本。
- Android：分别处理 API 26+ adaptive launcher、API 25 及以下 legacy launcher、可选 `roundIcon`、Android 13+/Android 16 QPR2 相关 monochrome 主题支持，以及 Google Play 独立的 512×512 商店图。adaptive 图标使用 108dp 图层和安全区；Play 图标使用自己的 PNG、色彩、大小和遮罩规则，不能用一张商店图替代包内 launcher 资源。

三平台的官方规则、版本差异和源链接见 [references/platform-rules.md](references/platform-rules.md)。需要细化从批准源图派生目标资源、组织导出清单或验证最终包时，再读取[导出与校验工作流](references/export-validation.md)。
